## 2. 総論: P-1/P-2/P-3の再構成に同意。ただし「移行窓」論法に過大適用がある

前提の再構成(測定ドリブンは測る対象が動いてから/案Aは引き渡し条件/初回導入が最大リスク)には同意する。

一方、本書全体を貫く「**移行コストが今だけゼロ**」論法が効くのは「**既存値の意味を変える変更**」だけである。**追加的変更には最初から窓は閉じない**:

- 新しいフィールドの追加(`request_ref`等)は、既存レコードで空になるだけで移行規則を要しない。後から足すコストは今足すコストと同じ
- 監査の新event_type追加も同様(提案書自身がF-6で指摘)

この区別により、[0]の中身(→§3・§4)とQ-Cの答え(→§6)が変わる。

## 3. Dq-3(Run集約状態): 案iに反対 — 「誰がINTERRUPTEDを書くのか」問題

提案書§6.3の**案i(中断を表すstatus値の追加)には、移行窓の開閉と無関係に反対する**。

集約状態は**Networkロックを保持するInvocationだけ**がrevision付きで更新する(仕様§10、D-24。凍結済みの単一書込主体原則)。ところが「中断」が起きる典型は**書き手が死ぬ瞬間**である:

| 中断の起き方 | 案iのstatus値を書けるか |
| --- | --- |
| プロセスkill・電源断・ホスト障害 | **書けない**(書き手が存在しない)。Runはどんな値を用意しても`RUNNING`のまま残る |
| graceful drain(lease喪失) | 書ける。ただしこのケースは既にInvocation側が`CANCELLED / NETWORK_LEASE_INTERRUPTED`で判別可能 |

つまり案iは「**書けるケースでは冗長、書けないケースでは無力**」。中断とは本質的に保存された状態ではなく、**観測時に導出される性質**(未完了 かつ lock owner不在/lease失効)であり、提案書自身が§6.2でその導出式を正しく書いている。「窓が開いている今なら本来望ましい案iを選べる」という論法は、**案iがいつ選んでも機能しない**ため成立しない。

### 対案(案ii-強化): 導出を一級市民にする

1. **`status --json`へ導出フィールドを追加** — 例: `activity: "LIVE" | "INTERRUPTED" | "IDLE"`(lock owner存在+lease生存→LIVE、未完了かつowner不在/失効→INTERRUPTED)。既存の`stale_candidate`と同じ材料の組合せで、read-only出力の追加のみ。**保存データ無変更・移行永久不要・killケース耐性あり・FDR再審議不要**
2. 案Aプラグインは同じ導出式で「対応が必要なRun」一覧を出す(提案書§6.2どおり)
3. 画面文言は「実行中」ではなく「**未完了**」とし、LIVE/INTERRUPTEDを別に表示する(§6.1の「担当者が待ち続ける」事故はこれで防ぐ)

## 4. Dq-1(順序): 概ね同意、3点の修正

### 4.1 [0]の中身の更新

- Dq-2: **完了済み**につき[0]から除外
- Dq-3: 上記のとおりstatus変更ではなく導出強化に置換
- 結果、**[0]に凍結仕様の変更は残らない**。[0]は「status activity導出(非意味論)+下記ブレーキ」に縮退する

### 4.2 案Aには「ほぼ無料のv0」がある

実行管理アプリはtemplateで一覧定義済みであり、「NODE_STATEのstatusがFAILED/UNKNOWN/BLOCKED」の一覧(blocked_by・status_reason表示付き)は**標準機能の一覧設定だけで作れる**。プラグインが必要なのはlockとの突合(INTERRUPTED導出)だけである。

提案: 案Aを分割する。

- **案A v0**: 一覧設定のみ(コード無し・即日級)。[3]より前に無条件で実施
- **案A v1**: 導出プラグイン。Q-Aの答え次第で[3]の前後いずれか

### 4.3 [2]の再定義 — 「リトライ先行」ではなく「ブレーキ先行」(R-2/Q-Bへの回答)

提案書§4.2-(b)には見落としがある: **「夜間に自動で直っている」はPhase 1+cronで既に実現している**。冪等FAILEDノードはcronの`--resume`毎に自動で再attemptされる(仕様§5.3、実機検証済み)。Phase 2のリトライポリシーを待つ必要はない。

欠けているのは逆方向の**ブレーキ**(P2-03: 同一ノード連続失敗N回で明示フラグなしでは着手しない)である。決定的に失敗するノードがattempt・API・レコードを無限に消費する問題は外部評価R2-4で確認済み。

- 分離可能性(Q-B): **明確にYes**。schedulerの着手判定に連続失敗条件を足すだけで、並列化・trigger_rule拡張と無関係
- 位置づけ: 「Phase 2の先行実装」ではなく「**本番導入前の小粒の安全装置**」(軽量なFDR再審議1件)
- backoff・宣言的ポリシー等の豊かさは実測後でよい

### 4.4 修正後の順序案

```text
[0'] status activity導出(FDR審議不要) + P2-03ブレーキ(軽量FDR審議)
[1'] 案A v0(一覧設定のみ)+ 一次対応1ページ(→Q-E)
        │        └ 案A v1(導出プラグイン)はQ-A次第で[3]の前後
[3]  初回本番導入(1業務・1ネットワーク)+ Dq-4確定 ← 中心である点は同意
[4]  実測(閾値は着手前に合意 — 提案書§8に同意)
[5]  案B(要求アプリ+ポーラー) / cancel伝播(P2-02)
[6]  並列化等 — 需要が出てから(同意)
[7]  案C — P-3成立時のみ(同意)
```

## 5. 提案書§3不変条件4への訂正(凍結仕様との不整合)

「旧保持者の停止確認は機械が行う。人の申告・証跡添付は理由であって確認ではない」は**凍結仕様と食い違う**。D-29はPhase 1 baselineとして`--stop-method manual`(runbookに従い人が収集・入力した停止証拠の監査付き検証)を正式に含む。受入28の「terminal状態のみ・fail-closed」は**自動回収経路**(cloud_run_job_execution等)の規律である。

訂正文言の提案:

> **無人経路(ポーラー・ボタン起点)から回収系を呼ぶ場合は機械確認(`local_pid` / `cloud_run_job_execution`)に限定する。人がCLIで行う`manual`停止確認は凍結仕様どおり有効である。**

案B/Cの受理範囲設計に直結するため、この訂正は必須と考える。
