## 「00_Run状況」ボードの読み方

ボードは未終端Runを1行ずつ表示します。activity 4値の意味と行動は下の「状態別の対応表」を参照してください。レコード番号はNETWORK_RUNの詳細画面へのリンクで、詳細でも同じactivityと根拠を確認できます。ボード末尾の「判定時刻」はactivity導出に使ったブラウザ時刻です。時刻や表示が不審な場合、または画面とCLIで判断が割れた場合は、**CLI `status --json`が正で、画面は補助**です。推測で操作せず二次対応者へ連絡してください。

## 状態別の対応表

| 見えたもの | 意味 | あなたの対応 |
| --- | --- | --- |
| 00に`LIVE`(緑) | lock ownerが当該Runに属しlease生存 — 実行中 | **待つ(触らない)** |
| 00に`IDLE`(灰) | `started_at`なし — 未開始 | **定期起動を待つ** |
| 00に`STOPPED`(黄) | CANCEL_REQUESTがREQUESTED/ACCEPTED — 意図停止(hold) | **止めた本人に確認**。解除は`RELEASE`要求 |
| 00に`INTERRUPTED`(赤) | LIVE、IDLE、STOPPEDのいずれでもない — 中断の疑い | **二次対応者へ連絡**(Run IDを添える) |
| 01にFAILED(status_reasonに`RETRY_BRAKE`が**ない**) | 失敗したが、次の定期実行で自動再試行されます | **何もしない**。翌朝も残っていたら連絡 |
| 01にFAILED(status_reasonに`RETRY_BRAKE:`が**ある**) | 同じ失敗が3回続いたため自動再試行を停止中 | **連絡**(SQLかデータの修正が必要です) |
| 01にUNKNOWN | 結果を確認できない状態。**触ると危険** | **即連絡**。何も操作しない |
| 01にBLOCKED | 上流の失敗待ち。それ自体は正常な連鎖 | 同じ一覧の上流(FAILED/UNKNOWN)側の行で判断 |
| 02に未完了Runが残り、01は空 | **途中で中断している可能性**(電源断・プロセス停止など) | **連絡**(「Run IDと画面の状態」を伝える) |
| 03_停止要求に行がある | 誰かが意図して止めています(`RELEASED`以外の間は再開されません) | 止めた本人・二次対応者に確認 |

## アプリからの再開・停止・解除

操作を依頼された場合は「kSQL-FlowNet 操作要求」アプリで**新しいレコードを追加**し、`run_id`、理由、次の操作種別を入力します。既存要求を編集して再利用しないでください。

| 操作種別 | 使う場面 | 操作後に確認すること |
| --- | --- | --- |
| `RERUN` | 原因修正済みのRunを再開する | 要求が`DONE`になる。`REJECTED`や`RETRY_BRAKE`なら二次対応者へ連絡 |
| `STOP` | 未完了Runを安全な区切りで止める | 要求が`DONE`でも、停止が効くのは**次ノード境界**。実行中SQLは途中停止しない |
| `RELEASE` | STOPによるholdを解除する | 解除だけで自動再開しない。ただし次の定期`resume`がRunを再開し得るため、再開してよい状態でだけ行う |

`rerun_from_node`は二次対応者から、原因修正後のRETRY_BRAKE解除として具体的なNode IDを指示された場合だけ入力します。UNKNOWNや非冪等Nodeを推測で指定しないでください。

要求が`REJECTED / STALE`なら、実行済みか未実行かを画面だけでは確定できません。**再要求は禁止**です。要求レコードIDとRun IDを控えて二次対応者へ連絡し、実行管理・監査履歴・JOBログの照合が終わるまで待ってください。

## してはいけないこと

- **実行管理アプリ・監査履歴アプリのレコードを編集・削除しない**(編集すると本体の書込みが失敗し、状態が壊れます。閲覧は自由です)
- JOBログアプリのレコードを編集・削除しない
- 復旧系の操作(resolve、force-unlock、レコード修正)を自分で行わない — すべて二次対応者の作業です
- `STALE`になった操作や結果不明の操作を、別レコードで繰り返さない

## 知っておくと混乱しないこと

- **「RUNNING」表示は「実行中」ではなく「未完了」の意味**です。本当に動いているかは二次対応者が確認できます(見た目がRUNNINGのまま止まっていることがあります)
- **停止要求(cancel)は、今動いているSQLの途中では止まりません**。次の区切り(ノード境界)まで待ってから止まります。1時間かかる処理の途中で止めても、止まるのは最大でその処理の完了後です
- 失敗→自動再試行→成功、は正常な動きです。朝の時点で01が空なら夜間に自動回復しています
