## 「00_Run状況」ボードの読み方

ボードは上段に「進行中のRun」、下段に「終了済み・対応が必要なRun」を1行ずつ表示します。activity 4値の意味と行動は下の「状態別の対応表」を参照してください。レコード番号はNETWORK_RUNの詳細画面へのリンクで、詳細でも同じactivityと根拠を確認できます。ボード末尾の「判定時刻」はactivity導出に使ったブラウザ時刻です。時刻や表示が不審な場合、または画面とCLIで判断が割れた場合は、**CLI `status --json`が正で、画面は補助**です。推測で操作せず二次対応者へ連絡してください。

エラー本文はボードと詳細画面にも表示されます。全文と履歴はJOBログの関連レコードを二次対応者が確認します。

## 新しい業務実行をSTARTする

STARTは、失敗した既存Runのやり直しではなく、**まだRunがない新しい業務実行単位を作る要求**です。失敗・中断したRunは下記の`RERUN`を使います。起票には次の2経路があります。

1. **ボードから起票(推奨)**: 「00_Run状況」上部の「新規実行」を押し、入力モード、`network_id`、キー、理由を入力します。ボタンと「処理待ちのSTART要求 N件」は、操作要求アプリが設定されている場合だけ表示されます。候補は過去実績による入力支援で、実際に起動可能かはサーバー側設定で判定されます。
2. **操作要求アプリへ直接起票**: 新しいレコードで`request_type=START`、`network_id`、下表のキー、理由を入力します。`run_id`、claim、状態、結果欄は入力・編集しません。

| 入力モード | 入力例 | 注意 |
| --- | --- | --- |
| 定期キー | `network_id=monthly-sales`、`scheduled_for=2026-09-01 00:00` | 対象期間だけを指定。ボードでは日本時間として入力します |
| 補正 | `network_id=monthly-sales`、`business_key=monthly-sales@2026-08-correction-1`、`scheduled_for=2026-09-01 00:00` | **補正キーと対象期間の両方が必須**です |
| explicit | `network_id=adhoc-export`、`business_key=ticket-12345` | 業務キーだけを指定します |

ポーラーは5分間隔のため、要求作成後は**最大5分ほどで処理を開始します**。`request_state=DONE`は「START要求の処理が完了した」という意味で、Runの成功を意味しません。作成されたRunの成否は「00_Run状況」ボードで確認します。

| START結果 | 対応 |
| --- | --- |
| `DONE / NOOP_ALREADY_SUCCESS` | 同じ業務キーのRunは既に成功済みです。表示されたRunをボードで確認し、再起票しません |
| `REJECTED / RUN_ALREADY_EXISTS` | 同じ業務キーの未完了Runがあります。新規STARTではなく、表示されたRunの状態を確認し、必要なら`RERUN`を使います |
| `REJECTED / MAX_ACTIVE_RUNS` | 同じnetworkの別Runが未完了です。blockerのRun IDを添えて二次対応者へ連絡し、STARTを繰り返しません |
| `REJECTED / LOCK_CONFLICT` | 競合中です。処理待ちに同じSTARTがないことを確認し、時間をおいて1回だけ再起票します。再び競合したら要求IDとnetworkを添えて二次対応者へ連絡します |
| `REJECTED / STALE` | まずボードに**新しいRunが出ていないか**確認します。出ていればそのRunを追跡します。出ていないことを二次対応者が確認できた場合だけ、新しいSTART要求を起票します |

## 状態別の対応表

| 見えたもの | 意味 | あなたの対応 |
| --- | --- | --- |
| 00に`LIVE`(緑) | lock ownerが当該Runに属しlease生存 — 実行中 | **待つ(触らない)** |
| 00に`IDLE`(灰) | `started_at`なし — 未開始 | **定期起動を待つ** |
| 00に`STOPPED`(黄) | CANCEL_REQUESTがREQUESTED/ACCEPTED — 意図停止(hold) | **止めた本人に確認**。解除は`RELEASE`要求 |
| 00に`INTERRUPTED`(赤) | LIVE、IDLE、STOPPEDのいずれでもない — 中断の疑い | **まずボードからリラン要求を1回**。要求の結果が`OK`以外(`REJECTED / LOCK_CONFLICT`を含む)・再中断・繰り返す場合はRun IDを添えて連絡 |
| 01にFAILED(status_reasonに`RETRY_BRAKE`が**ない**) | 失敗したが、次の定期実行で自動再試行されます | **何もしない**。翌朝も残っていたら連絡 |
| 01にFAILED(status_reasonに`RETRY_BRAKE:`が**ある**) | 同じ失敗が3回続いたため自動再試行を停止中 | **連絡**(SQLかデータの修正が必要です) |
| 「終了済み・対応が必要なRun」または01にUNKNOWN | 結果を確認できない状態。**触ると危険** | ボードのコピーボタンで**Run IDをコピーして即連絡**。何も操作しない |
| 01にBLOCKED | 上流の失敗待ち。それ自体は正常な連鎖 | 同じ一覧の上流(FAILED/UNKNOWN)側の行で判断 |
| 02に未完了Runが残り、01は空 | **途中で中断している可能性**(電源断・プロセス停止など) | **連絡**(「Run IDと画面の状態」を伝える) |
| 03_停止要求に行がある | 誰かが意図して止めています(`RELEASED`以外の間は再開されません) | 止めた本人・二次対応者に確認 |

## ボードまたは操作要求アプリからの再開・停止・解除

操作には次の2経路があります。

1. **ボードから起票(推奨)**: 「00_Run状況」の対象行で「リラン要求」「停止要求」「解除要求」を押し、理由を入力して確認します。「終了済み・対応が必要なRun」のFAILED/CANCELLEDもボードからリラン要求できます。
2. **操作要求アプリ直接(従来)**: 「kSQL-FlowNet 操作要求」アプリで新しいレコードを追加し、`run_id`、理由、操作種別を入力します。

どちらの経路でも既存要求を編集して再利用しないでください。完了は操作要求レコードの`request_state`と`result_code`で確認します。

| 操作種別 | 使う場面 | 操作後に確認すること |
| --- | --- | --- |
| `RERUN` | INTERRUPTEDを1回再開する、または原因修正済みのRunを再開する | `request_state=DONE`かつ`result_code=OK`を確認する。`REJECTED / LOCK_CONFLICT`、`RETRY_BRAKE`など結果が`OK`以外、再中断、同じ操作を繰り返す状況なら二次対応者へ連絡 |
| `STOP` | 未完了Runを安全な区切りで止める | 要求が`DONE`でも、停止が効くのは**次ノード境界**。実行中SQLは途中停止しない |
| `RELEASE` | STOPによるholdを解除する | 解除だけで自動再開しない。ただし次の定期`resume`がRunを再開し得るため、再開してよい状態でだけ行う |

STOPしたRunは、**止めた直後は上のブロック(黄)、完全に止まると下の要対応ブロックへ**移ります。

M3実機受入では、kill起因のINTERRUPTEDに対するリラン要求が`REJECTED / LOCK_CONFLICT`になりました。この場合は再要求せず、停止確認とlock回収が必要なため二次対応者へ連絡してください。

`rerun_from_node`は二次対応者から、原因修正後のRETRY_BRAKE解除として具体的なNode IDを指示された場合だけ入力します。UNKNOWNや非冪等Nodeを推測で指定しないでください。

RERUN/STOP/RELEASE要求が`REJECTED / STALE`なら、実行済みか未実行かを画面だけでは確定できません。**再要求は禁止**です。要求レコードIDとRun IDを控えて二次対応者へ連絡し、実行管理・監査履歴・JOBログの照合が終わるまで待ってください。STARTは上のSTART専用手順に従います。

## してはいけないこと

- **実行管理アプリ・監査履歴アプリのレコードを編集・削除しない**(編集すると本体の書込みが失敗し、状態が壊れます。閲覧は自由です)
- JOBログアプリのレコードを編集・削除しない
- 復旧系の操作(resolve、force-unlock、レコード修正)を自分で行わない — すべて二次対応者の作業です
- `STALE`になった操作や結果不明の操作を、二次対応者の照合が終わる前に別レコードで繰り返さない

## 知っておくと混乱しないこと

- **「RUNNING」表示は「実行中」ではなく「未完了」の意味**です。本当に動いているかは二次対応者が確認できます(見た目がRUNNINGのまま止まっていることがあります)
- **停止要求(cancel)は、今動いているSQLの途中では止まりません**。次の区切り(ノード境界)まで待ってから止まります。1時間かかる処理の途中で止めても、止まるのは最大でその処理の完了後です
- 失敗→自動再試行→成功、は正常な動きです。朝の時点で01が空なら夜間に自動回復しています
