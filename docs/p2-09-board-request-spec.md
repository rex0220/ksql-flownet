## 1. 目的と非目的

**目的**: Run状況ボード(P2-08)から、リラン・停止・解除の**操作要求レコードを起票**できるようにする。現状の「ボードで異常を発見→操作要求アプリを開いて手入力」という2画面動線を1画面に短縮する。

**原則**: ボタンは**操作要求アプリへレコードを1件作るだけ**。実行は稼働中のポーラー(P2-01)経由の非同期(約5分以内)であり、プラグインは判断・実行をしない。書込先は操作要求アプリのみ — **実行管理・監査アプリへは今後もGET限定**(機械専用制約は不変)。

**非目的**: resolve-node・force-unlock・`--approved-by`など判断を伴う復旧操作のアプリ化(CLIのまま)。即時実行・ポーラー周期の変更。受理範囲の変更(P2-01の固定受理範囲をそのまま使う)。モバイル。

## 2. 操作メニュー(activity連動の出し分け)

| 表示場所・状態 | ボタン | 起票内容 | ダイアログの必須注意文言 |
| --- | --- | --- | --- |
| ボード行: `INTERRUPTED`(赤) | リラン要求 | `RERUN` + run_id | 「リランで直らない中断もあります。原因不明の場合は二次対応者へ連絡してください」(既存の連絡導線は残す) |
| ボード行: `LIVE`(緑) | 停止要求 | `STOP` + run_id | 「停止は次のノード境界まで効きません(実行中SQLは完走します)」 |
| ボード行: `STOPPED`(黄) | 解除要求 | `RELEASE` + run_id | 「解除後、次の定期resumeがRunを再開し得ます。再開してよい状態でだけ解除してください」 |
| ボード行: `IDLE`(灰) | (ボタンなし) | — | 操作不要(定期起動を待つ) |
| レコード詳細画面: 終端`FAILED` / `CANCELLED` | リラン要求 | `RERUN` + run_id(+任意`rerun_from_node`) | ボードは未終端限定のため**FAILED Runのリトライは詳細画面から**。`rerun_from_node`は「二次対応者からRETRY_BRAKE解除等で具体的なNode IDを指示された場合のみ入力」の注意書き付き上級欄 |
| レコード詳細画面: 上記以外 | ボードと同じ出し分け | — | — |

共通仕様:

1. **理由必須**の入力ダイアログ→操作内容の確認→POST。成功時「要求 #\<record_id\> を作成しました。約5分以内にポーラーが処理します」+**要求レコードへのリンク**を表示
2. 二重送信防止(送信中はボタン無効化)。POST失敗はエラー明示のみ(自動リトライしない — 人が押し直す)
3. **受理判定をプラグインへ持たせない**: ボタンの出し分けは無駄な要求を減らす親切であって審査ではない。正の受理・拒否はポーラー+CLIの既存規則(P2-01 §4)が行い、拒否理由は要求レコード(02_拒否一覧)に残る
4. **要求者の真正性は不変**: レコード作成者=kintoneログインユーザー(プラグインは代筆・偽装をしない。要求フィールドへ操作者名を書かない)
5. 起票するフィールドは`request_type` / `run_id` / `reason`(+詳細画面のみ`rerun_from_node`)の人間欄だけ。機械欄(`request_state`等)は初期値のまま触らない

## 3. 実装方式

- プラグイン設定へ**操作要求アプリID**を追加(2項目目。`auditAppId`と同じ検証・保存方式)。未設定の場合はボタンを表示せず、従来どおりの読み取り専用ボードとして動作する(**後方互換 — 設定するまで挙動不変**)
- POSTは`/k/v1/record.json`(単票)のみ。実行者権限で書く(APIトークン不使用) — 一次対応者に必要な権限: 操作要求アプリの**レコード追加**
- ダイアログはプラグイン自前DOM(kintone内部DOM非依存)。reason等の表示・格納はtextContent系のみ(P2-08と同じXSS規律)
- 起票後のボード再読込は自動で1回行い、必要なら「01_未処理要求」一覧への導線を示す

## 4. P2-08仕様の改訂点(本仕様の採用と同時に反映)

- P2-08 §4「書込みゼロ(G-09)」→「**実行管理・監査アプリへはGET限定。書込は操作要求アプリへのレコードPOSTのみ**(cursor作成・Bulk・PUT/DELETEは引き続き禁止)」
- P2-08受入4(実機ネットワーク確認)→ 上記の範囲で再定義(操作時のPOSTは操作要求アプリの`record.json`宛1件のみであること)

## 5. 受入基準(実機E2E)

1. ボードのINTERRUPTED行からリラン要求→要求レコード作成(作成者=操作ユーザー)→ポーラー受理→resume完走→要求`DONE`(一気通貫)
2. LIVE行から停止要求→次ノード境界で停止→`DONE`。STOPPED行から解除要求→hold解除→`DONE`
3. 詳細画面の終端FAILED Runからリラン要求→resume完走。`rerun_from_node`指定がCLIの`--rerun-from`として効く
4. 拒否系: 出し分けをすり抜けた要求(例: ボタン表示直後に状態が変わったRunへのRERUN)がポーラーで`REJECTED`+理由になり、プラグイン側は壊れない
5. ネットワーク実機確認: 閲覧操作はGETのみ、起票操作は操作要求アプリへのPOST 1件のみ。実行管理・監査へのPOST/PUT/DELETEがない
6. 要求アプリID未設定時はボタンが出ず、既存P2-08の読み取り専用動作と完全一致
7. 二重クリックで要求が2件できない。reason空は送信不可
8. 文書: 一次対応1ページの操作手順を「ボードから起票(推奨)/操作要求アプリ直接(従来)」の2経路へ更新し、注意文言(ノード境界・RELEASE後の再開・rerun_from_node)が本仕様と一致
