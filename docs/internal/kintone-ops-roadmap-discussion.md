## 3. Dq-3(Run集約状態): 案iに反対 — 「誰がINTERRUPTEDを書くのか」問題

提案書§6.3の**案i(中断を表すstatus値の追加)には、移行窓の開閉と無関係に反対する**。

集約状態は**Networkロックを保持するInvocationだけ**がrevision付きで更新する(仕様§10、D-24。凍結済みの単一書込主体原則)。ところが「中断」が起きる典型は**書き手が死ぬ瞬間**である:

| 中断の起き方 | 案iのstatus値を書けるか |
| --- | --- |
| プロセスkill・電源断・ホスト障害 | **書けない**(書き手が存在しない)。Runはどんな値を用意しても`RUNNING`のまま残る |
| graceful drain(lease喪失) | 書ける。ただしこのケースは既にInvocation側が`CANCELLED / NETWORK_LEASE_INTERRUPTED`で判別可能 |

つまり案iは「**書けるケースでは冗長、書けないケースでは無力**」。中断とは本質的に保存された状態ではなく、**観測時に導出される性質**(未完了 かつ lock owner不在/lease失効)であり、提案書自身が§6.2でその導出式を正しく書いている。「窓が開いている今なら本来望ましい案iを選べる」という論法は、**案iがいつ選んでも機能しない**ため成立しない。

### 対案(案ii-強化): 導出を一級市民にする

1. **`status --json`へ導出フィールドを追加** — 例: `activity: "LIVE" | "INTERRUPTED" | "IDLE"`(lock owner存在+lease生存→LIVE、未完了かつowner不在/失効→INTERRUPTED)。既存の`stale_candidate`と同じ材料の組合せで、read-only出力の追加のみ。**保存データ無変更・移行永久不要・killケース耐性あり・FDR再審議不要**
2. 案Aプラグインは同じ導出式で「対応が必要なRun」一覧を出す(提案書§6.2どおり)
3. 画面文言は「実行中」ではなく「**未完了**」とし、LIVE/INTERRUPTEDを別に表示する(§6.1の「担当者が待ち続ける」事故はこれで防ぐ)

## 4. Dq-1(順序): 概ね同意、3点の修正

### 4.1 [0]の中身の更新

- Dq-2: **完了済み**につき[0]から除外
- Dq-3: 上記のとおりstatus変更ではなく導出強化に置換
- 結果、**[0]に凍結仕様の変更は残らない**。[0]は「status activity導出(非意味論)+下記ブレーキ」に縮退する

### 4.2 案Aには「ほぼ無料のv0」がある

実行管理アプリはtemplateで一覧定義済みであり、「NODE_STATEのstatusがFAILED/UNKNOWN/BLOCKED」の一覧(blocked_by・status_reason表示付き)は**標準機能の一覧設定だけで作れる**。プラグインが必要なのはlockとの突合(INTERRUPTED導出)だけである。

提案: 案Aを分割する。

- **案A v0**: 一覧設定のみ(コード無し・即日級)。[3]より前に無条件で実施
- **案A v1**: 導出プラグイン。Q-Aの答え次第で[3]の前後いずれか

### 4.3 [2]の再定義 — 「リトライ先行」ではなく「ブレーキ先行」(R-2/Q-Bへの回答)

提案書§4.2-(b)には見落としがある: **「夜間に自動で直っている」はPhase 1+cronで既に実現している**。冪等FAILEDノードはcronの`--resume`毎に自動で再attemptされる(仕様§5.3、実機検証済み)。Phase 2のリトライポリシーを待つ必要はない。

欠けているのは逆方向の**ブレーキ**(P2-03: 同一ノード連続失敗N回で明示フラグなしでは着手しない)である。決定的に失敗するノードがattempt・API・レコードを無限に消費する問題は外部評価R2-4で確認済み。

- 分離可能性(Q-B): **明確にYes**。schedulerの着手判定に連続失敗条件を足すだけで、並列化・trigger_rule拡張と無関係
- 位置づけ: 「Phase 2の先行実装」ではなく「**本番導入前の小粒の安全装置**」(軽量なFDR再審議1件)
- backoff・宣言的ポリシー等の豊かさは実測後でよい

### 4.4 修正後の順序案

```text
[0'] status activity導出(FDR審議不要) + P2-03ブレーキ(軽量FDR審議)
[1'] 案A v0(一覧設定のみ)+ 一次対応1ページ(→Q-E)
        │        └ 案A v1(導出プラグイン)はQ-A次第で[3]の前後
[3]  初回本番導入(1業務・1ネットワーク)+ Dq-4確定 ← 中心である点は同意
[4]  実測(閾値は着手前に合意 — 提案書§8に同意)
[5]  案B(要求アプリ+ポーラー) / cancel伝播(P2-02)
[6]  並列化等 — 需要が出てから(同意)
[7]  案C — P-3成立時のみ(同意)
```

### 9.2 「移行窓」論法の過大適用: 全面的に認める

### 9.3 Dq-3: **案i を取り下げる**

§3 の反論は正しい。反論しない。

決め手は「中断が起きる典型は**書き手が死ぬ瞬間**である」という指摘である。集約状態の単一書込主体原則(D-24)の下では、kill・電源断・ホスト障害のケースで `INTERRUPTED` を書ける主体が存在しない。したがって案i は「書けるケースでは冗長、書けないケースでは無力」であり、**移行窓の開閉と無関係に、いつ選んでも機能しない**。提案書§6.3 の「窓が開いている今なら本来望ましい案i を選べる」は前提から誤っていた。

対案(案ii-強化: `activity` 導出)を支持する。その上で2点を設計に加えることを提案する。

**(1) 導出式の単一正本を決める。** `status --json` と案Aプラグインの2箇所で同じ導出を独立に実装すると、必ずドリフトする。**画面とCLIが違うことを言う**のは、P-2 の担当者にとって最悪の部類の事故である。導出規則を仕様の1箇所に定義し、プラグイン側はそれを引用する(または `status --json` の出力を使う)形にしたい。

**(2) `IDLE` と `INTERRUPTED` の境界を定義する。** 「未完了かつ owner 不在」は同じでも、担当者にとって意味が正反対である。

- `started_at` が null → **まだ始まっていない**(放置してよい場合がある)
- `started_at` があり、以後 owner 不在 → **途中で止まっている**(必ず対応が要る)

一次対応1ページの分岐がここで変わるため、3値の定義は画面設計より先に固定したい。

### 9.4 §4.3(ブレーキ先行): 認める。しかも提案側の自己矛盾だった

指摘は正しい。冪等 `FAILED` は cron の `--resume` ごとに自動再attemptされるため、「夜間に自動で直っている」は Phase 1 + cron で既に実現している。提案書§4.2-(b) は誤りであり、撤回する。

**さらに悪いことに、これは提案側の自己矛盾である。** 同じ討論の初期に「冪等 `FAILED` は resume ごとに無条件で `WAITING` に戻るため、cron が毎時叩くと決定的失敗ノードが無限に attempt を積む」と指摘しておきながら、後段で「リトライポリシーを入れれば自動で直る」と書いた。**欠けているのはリトライではなくブレーキである**という §4.3 の整理が正しい。`P2-03` を `[0']` に置くことに同意する。

実装にあたり、2点を設計判断として明示しておきたい。

**(1) 連続失敗カウントの持ち方。** Node State にカウンタを持たせると凍結済みスキーマに触れ、`revision` 競合の影響も受ける。Attempt 履歴から数える場合、仕様§6.4 の「`max(attempt_no)` 検索に依存しない」原則は**採番**についての規律なので抵触しないと読めるが、**着手判定ごとに履歴検索が1回増える**。Control Plane 使用量(受入28)に乗る点も含めて、どちらを採るか決めておきたい。

**(2) `LOCK_CONFLICT` をカウントに含めない。** 仕様§8.2 は `LOCK_CONFLICT` を「SQL実行失敗回数には数えない」と定めている。ブレーキの連続失敗カウントも同じ扱いにすべきである。単体ジョブと競合しただけでブレーキがかかると、正常な運用が止まる。

### 9.6 Q-D への回答に対する補強: 本ラウンド最大の発見

`DISTINCT_APPROVER_REQUIRED`(D-13)を確認した。**非冪等ノードの `SUCCESS` 解決には、`requested_by`・`service_principal` と異なる `--approved-by` が必須**である。

「これは案C の論点ではなく Phase 1 の運用開始条件である」という指摘に同意する。**一人体制では、非冪等ノードを含むネットワークは今日すでに詰まりうる。** これは本討論で誰も指摘していなかった、最も優先度の高い発見だと考える。

Dq-4 に対して、技術側から3点を追加したい。

**(1) 初回導入の対象業務に技術的な選定基準を足す。** 承認者問題を回避する最も安価な方法は、**非冪等ノードを含まないネットワークを初回対象に選ぶ**ことである。集計・抽出・更新系だけで閉じる業務なら、`--approved-by` が要る場面自体が発生しない。通知・請求・外部連携を含む業務は2件目以降に回す。

**(2) 承認者を開発者に置く場合、それは実質的にベンダーサポートである。** 応答時間(SLA)を決めないと、夜間の詰まりが翌営業日まで残る。P-3 が「可能性あり」の段階でも、**承認者の割当だけは初回導入前に決めておく必要がある**。

**(3) 承認者不在時の縮退運用を先に決める。** 少なくとも次の選択肢を Dq-4 で比較したい。

- (a) 非冪等ノードを含む業務を初回導入対象から外す(上記(1))

## 13. PRE-06設計決着(停止要求の置き場所)と同一ラウンド化

- 追記日: 2026-08-31
- 双方合意: **置き場所はstate appレコード(案B)で確定**

### 13.1 決め手の序列(合意)

1. **Cloud Run Jobs移行でローカルフラグは確実に捨てることになる**(実行毎にコンテナが入れ替わる。停止確認adapterに`cloud_run_job_execution`がある以上、移行は構想の射程内)
2. fail-closed整合: kintoneが読めずcancel要求を確認できない状況では同時にheartbeatも失敗しており、`LEASE_UNCERTAIN`のdrainで次ノードはどのみち起動しない。cancel読取失敗の特別扱いが不要
3. 監査・別ホスト対応(当初の理由)は副次
4. ノード境界ごとのGET+1はコスト論点にならない

### 13.2 設計条件(合意3件+担当CC追加1件)

1. **独立record_type(`CANCEL_REQUEST`等)とし、orchestratorが書くレコード(Lock/Run)に相乗りしない** — CLIの書込みが$revisionを進めorchestratorのheartbeat・集約更新をREVISION_CONFLICTさせるため(F-1制約は機械の書き手同士にも当てはまる)
2. **要求モデルを案Bと揃える**: `run_id`単位の状態機械`REQUESTED → ACCEPTED → DONE/RELEASED`。消費済み要求が次のRunを巻き込まず、PRE-06がそのまま案Bの要求モデルのプロトタイプになる([5]で作り直しが出ない)
3. **PRE-01との相互作用**: cancel停止後のRunは「未完了・owner不在・開始後」であり、現行3値定義では`INTERRUPTED`と**見分けがつかない**。しかもPRE-06導入後は正常操作の結果として日常的に発生する。→ **activityへ意図停止の区別を導入**(候補: 4値目`STOPPED`。導出材料は最新Invocationの停止系result_codeまたはcancel要求レコード — killと異なりgraceful停止は書き手が生きているため、保存ベースの導出が成立する)。3値定義(§10.2)とtest vectorの確定はPRE-06と不可分のため、**PRE-01をPRE-02/06と同一FDRラウンドへ統合**する
4. **(担当CC追加)one-shotかholdか**: cancel受理が「当該Invocationの停止」だけ(one-shot)だと、**次のcron `--resume`が最短1時間後に同じRunを再開してしまい、「今日は止めたい」が止まらない**。誤データ流入・締め中断というPRE-06の動機に照らすと、既定は**hold(明示解除まで再開拒否)**が妥当と考える。案: 要求が`ACCEPTED`のままの間、ensure-runはresumeを`RUN_ON_HOLD`(fail-closed、阻害要求IDを表示)で拒否し、`cancel-run --release`で`RELEASED`へ遷移させて再開可能にする。activityの`STOPPED`導出はこのhold状態を第一材料にできる。この点は同一FDRラウンドの審議対象とする
