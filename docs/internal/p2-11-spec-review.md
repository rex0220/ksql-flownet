## 0. 良い点(維持すべき設計判断)

- **FlowNet本体無改修+既存安全装置を最終裁定に置く構成**が一貫している。重複禁止INSERT・allowlist・CLI検証という既に実機で効いている3層に判定を委ね、ポーラーの事前チェックを「親切な拒否理由」に限定する切り分けは、P2-01/P2-09で確立した哲学の正しい延長。
- **「allowlist掲載=アプリからの起動を許可するリリース判断」**という運用線の言語化。権限をkintone側で設計しようとせず、VPS上のファイル編集(二次対応者作業)へ寄せたのは、権限モデルを増やさない点で正しい。
- **2段UI**(要求アプリ直接 → ボードボタン)。第1段だけで受入1〜4・6が閉じるので、M3で価値を確定してからUIへ進める分割になっている。
- 「即時性は最大5分」を非目的(§1)と留意点(§8)の両方に書いている。P2-09の指摘7(開始と完了の混同)と同型の失敗を先回りできている。

## 1. Blocking(M0で決着が必要)

### B-1. 起動コマンドの正が未定義 — `--resume`の有無で意味が変わる

§2の擬似コードは `run-network <定義パス> --json` で、**業務キー引数(`--business-key` / `--scheduled-for`)も`--resume`の有無も書かれていない**。ここが未定なまま実装へ渡すと、以下の分岐で仕様の意味が変わる。

| 実装 | 既存の未完了Runがあるとき | 帰結 |
| --- | --- | --- |
| `--resume` を付ける | **resumeされる**(Invocation作成 → G-07により要求は`DONE`) | STARTがRERUNの裏口になる |
| `--resume` を付けない | Phase 1 §2.1「未完了なら`--resume`/`--resume-run`を案内」= 起動せず案内 | §4の期待どおり |

**`--resume`を付けた場合が危険**: P2-01のRERUN受理条件(G-01 終端SUCCESS拒否 / G-02 live owner検出 / hold / `resume_allowed` / `lifecycle_status`)を**すべて迂回して既存Runが再開される**。要求種別はSTARTなので、監査上も「新規起動のつもりが本番Runの再開だった」と読めない。特に`scheduled_period` networkでは、業務キーが夜間cronの生成値と一致しうるため(B-2(a)参照)、**「臨時集計を投げたら夜間の失敗Runが勝手に再開された」が現実的に起きる**。

対応(いずれもM0で確定):

1. §2へ「ポーラーは`--resume`を**付けない**」を明示的な禁止として書く。実装計画のチェック項目にも入れる。
2. §2の擬似コードをキー引数込みの正確な形へ直す
   (`run-network <定義パス> --business-key <key> --json` / `--scheduled-for <ISO> --json`)。
3. **重複案内時のJSON契約を確認する**。ポーラーは§4の「未完了→REJECTED+既存run_id表示」を実現するために、Invocation作成前に終わるこの経路でも`run_id`を受け取る必要がある。P2-01 G-04が定義した`--json`出力(`outcome / run_id / invocation_id / ...`)がこの経路でも`run_id`を載せるか未確認。載らないならCLI表示境界の小改修が要る(P2-01が本体無改修原則から明示的に分離した範囲内なので、原則は壊れないが**作業として計上されていない**)。
4. `outcome`値とG-07分類の対応表を§4へ追加(NEW作成 / 完了済みNO-OP / 未完了案内 / 検証拒否 → `DONE` / `DONE(NOOP)` / `REJECTED` の写像)。

### B-2. §1の主目的「締めのやり直し・補正Run」が、§3〜§4の受理範囲では起動できない可能性が高い

2つの制約が重なって、**最も起動したいnetworkを両方から塞いでいる**。

**(a) キー排他ルールが補正Runを禁じている**

§3は「`business_key`は`business_key_policy: explicit`のnetwork用」「`scheduled_for`は`scheduled_period`のnetwork用」「両方・不足はREJECTED / KEY_POLICY_MISMATCH」としている。

しかし補正キー `monthly_close@2026-08-correction-1` が必要になるのは `scheduled_period` の月次締めであり、Phase 1 §2.1 は「定義を変更して再度実行する業務上の必要がある場合は、`monthly_close@2026-08-correction-1` のように別の`business_key`を明示する」、§9 は「backfill、correction、`type = explicit`では`--business-key`を明示する」と、**correctionでの`--business-key`明示指定を許可している**。§3のルールはこれを禁止してしまい、§1の目的・§0の正本参照(§2.1の補正キー想定形)と自己矛盾する。

→ **`scheduled_period` networkに対する`business_key`直接指定(correction経路)を受理範囲に含めるか**を決める。含めるなら§3の「どちらか一方」ルールを「`scheduled_period`は`scheduled_for`(定期同一キー)または`business_key`(correction)のいずれか」へ緩め、REJECTED条件を書き直す。含めないなら§1から「締めのやり直し・補正Run」を落として目的を実態へ合わせる(その場合、本仕様の価値は「臨時集計・データ修正バッチ」だけになる)。

**(b) 非冪等ノードの一律拒否**

§4は「networkに`idempotent: false`のノードが1つでもあれば REJECTED / NETWORK_NOT_IDEMPOTENT」とする。しかしPhase 1仕様の代表例 `monthly_close` は末端に `send_invoice: idempotent: false` を持つ。**締め系のnetworkは通知・請求・外部連携を末端に置くのが普通**なので、network単位の一律拒否では**アプリから起動できるnetworkが実質ゼロ〜1本になりかねない**。

→ M0の判断材料として、**実在networkの棚卸し表**(network_id / `business_key_policy.type` / 非冪等ノードの有無 / STARTで起動可否)を1枚出すことを提案する。開放対象が0〜1本なら、この受理範囲では仕様の投資対効果が成立しない。

**代案**: 一律拒否ではなく **allowlistのエントリ単位で `app_start: true|false`(既定false)を持たせる**。§2-3が既に「掲載=リリース判断」という運用線を引いているので、粒度を揃えられる。非冪等を含む締めnetworkも「この1本だけは運用判断で開放」ができ、fail-closedは既定falseで担保される。定義から自動判定するより、判断した人が残る点でも監査向き。

## 2. 要修正(矛盾・根拠の誤り)

### C-1. 非冪等拒否の**根拠**が誤っている

§1非目的「非冪等ノードを含むnetworkの起動(`--approved-by`を要する操作はCLI専権)」、§4「非冪等の起動はCLI専権」——`--approved-by`は **`resolve-node`(UNKNOWN / 非冪等FAILEDの手動解決)** の要件であって、非冪等ノードを含むnetworkの**新規起動**に承認は要らない。現に定期cronは毎月 `send_invoice` を承認なしで実行している。

さらにPhase 1 §7.2の2026-08-31精緻化は「**未実行(`latest_attempt_no = 0`)の非冪等ノードは`--resume`と同様に初回attemptとして実行できる。attemptを持たないノードの初回実行に二重実行リスクは存在しない**」と明言している。新規Runは全ノードが未実行なので、**二重実行リスクという意味では新規起動に非冪等固有の危険はない**。

危険なのは別のもの——「アプリの追加権限を持つ人が誰でも押せる経路で、外部への副作用(請求・通知)が発火する」という**権限とレビューの話**。根拠を書き換えないと、レビュー時に「では`--approved-by`を付ければ良いのでは」という誤った着地をする。C-1の書き換えとB-2(b)の代案はセットで扱える。

### C-2. §4表と受入4の非対称

受入4は「run_id記入済みSTART」の拒否を求めているが、§4の受理範囲表に対応する行がない(§3の本文にのみ「空必須」とある)。§7 M0のチェック項目「仕様条件追加=受入同時追加」(P2-09の教訓)の**逆方向の漏れ**。§4表へ `RUN_ID_NOT_ALLOWED` 行を追加する。

### C-3. 受入3がB-1の未決着に依存している

「未完了Runがある場合はREJECTED+既存run_id案内」は、B-1の実装が`--resume`なし かつ 重複案内経路で`run_id`がJSONに載る場合にのみ成立する。B-1確定後に書き直す。

### C-4. 第2段の重複ガードは、P2-09の実装を流用できない

P2-09 §3共通4/受入15の処理待ちガードは、**表示中Runの`run_id`集合で`in (...)`GET**する実装。STARTには`run_id`がない(空必須)ため、`network_id + business_key/scheduled_for` を鍵にした**別クエリの新規実装**になる。§5は「重複ガード(同一network_id+キーの処理待ちSTART要求)…P2-09の意匠・共通仕様(§3)を踏襲」の一行で済ませているが、これは意匠の踏襲では足りない。

あわせて置き場所の問題: 処理待ちのSTARTは**対応するRunがまだ存在しないのでボードのどの行にも出せない**。ヘッダー側(新規実行ボタンの近く)に「処理待ちのSTART要求 N件」を出す等、表示位置をM0で決める。fail-open方針とGET 403の扱い(P2-09 §3共通2/3)を明示的に継承すると書いておく。

### C-5. network候補(過去Run実績)とallowlistの非対称

§5第2段は候補を`NETWORK_RUN`の`network_id` distinctから集める。しかし:

- **allowlist外だが過去に実行実績のあるnetworkが候補に出る** → 選ぶと必ずREJECTED。P2-09 第2巡指摘2で先回り防止した「押しても必ず拒否されるボタン」と同型の欠陥が、候補リストの形で復活する。
- 逆に**allowlist掲載済みで未実行のnetworkは候補に出ない**(初回起動が最も候補を必要とする場面なのに)。
- kintoneにDISTINCTはないため、実装はレコードのページング+クライアント側集約になる。件数上限で欠落しうる。

→ 候補は「参考候補(過去実績)」と明示ラベルし、自由入力を主、候補を補助とする。あるいは第2段では候補収集を落とし、REJECTED理由の明快さ(`NETWORK_NOT_ALLOWED`+allowlistへの掲載依頼導線)で受け止める割り切りも十分ありうる。

## 4. 運用・設計上の注意(採否は判断)

- **E-1. profileが未定義**。allowlistは`network_id → 定義パス`のみで、profileはポーラーの環境変数由来。複数profile運用があるなら要求レコードにprofile欄が必要。単一profile前提ならその前提を§2へ明記(将来の穴を塞ぐ)。
- **E-2. STARTのSTALEは後始末の意味が違う**。P2-01 G-05のSTALEは「実行有無・結果を確定不能、自動再実行しない」。RERUNなら対象Runを見れば済むが、**STARTは「Runが作られたかどうか自体が不明」**になる。留意点と一次対応1ページへ「STARTがSTALEになったら、ボードに新しいRunが出ていないか確認してから再起票」の一文を。
- **E-3. 同一networkへの同時STARTはロック競合になる**。P2-01は多重ポーラーを許容する設計(受入6)なので、cron重複起動下で別キーの2件のSTARTが同時に走ればNetworkロックで片方が落ちる。拒否理由一覧に含め、「時間をおいて再起票」で受け止める(異常ではない)ことを文書化。
- **E-4. `max_active_runs`(既定1)が事実上の歯止め**になっている点を§8の権限線の議論へ書き加えると締まる。「allowlistへ載せる=誰でも起動できる」の不安に対し、**同一networkで未完了Runは1本までという既存のブレーキが効く**のは重要な緩和材料。
- **E-5. G-07により、Runが失敗しても要求は`DONE`になる**。STARTの`DONE`は「起動できた」であって「業務が終わった」ではない。P2-09 指摘7で分離した文言規律をSTARTにも適用し、第2段の成功表示・要求アプリの一覧名で混同させないこと。§5の「Runが作成されるとボードに現れます」は良い方向だが、**要求の終端表示側**にも同じ手当が要る。
- **E-6. 用語**: §4表の「同一`network_id+業務キー`」は、正確には `profile + network_id + business_key`(Phase 1 §2.1)。profileを略すなら E-1 の単一profile前提とセットで。
