### X-1. 「処理前取消」はP2-11に内包すべきか、切り出すべきか

§9が自ら「**全request_type共通の汎用改善**」と書いているとおり、取消はSTART固有の機能ではありません。そして影響範囲は本仕様の外に出ています:

| 変更先 | 内容 | その文書の状態 |
| --- | --- | --- |
| P2-01 §4 状態機械 | `REQUESTED → CANCELLED` 終端を追加 | **REVIEWED** |
| P2-01 §3 権限表 | 「人はkintone画面から追加のみ」→ 追加+編集 | **REVIEWED** |
| P2-01 §5 処理順 | claim時の`cancel_requested`検知を挿入 | **REVIEWED** |
| P2-08 §4 / P2-09 §5 | G-09境界(POST限定 → POST+PUT) | **REVIEWED** |
| 要求アプリテンプレート | `cancel_requested`欄 + `request_state`へ`CANCELLED` | 本番稼働中 |

v5冒頭は「凍結仕様の変更なし — P2-01とP2-08/09の**拡張**」と書いていますが、**REVIEWED文書の状態機械と権限モデルを書き換えるのは拡張ではなく改訂**です。§3の「変更は取消の追加のみ」という但し書きは正直ですが、位置づけを変えるものではありません。

前例があります。P2-09 第2巡指摘1は、まさに同じ形(「実行管理アプリの状態を書く新しい経路が要る」)に直面したとき、**P2-11へ内包せずP2-10として切り出し**、「状態を書く新CLIのため個別レビュー」と判断しました。今回の取消は、それと同格かそれ以上(権限モデルに触る)の変更です。

選択肢:

- **(a) P2-12として切り出す** — P2-11はSTARTだけで閉じ、5巡のレビューを経た状態でFROZENにできる。取消は全request_type共通の改善として単独でレビュー・受入を組める(START未実装でも価値が出る)。**推奨。**
- **(b) 内包する** — その場合、以下が必須:
  - M0改訂リストへ **D-4: P2-01 §3/§4/§5の改訂**(状態機械への`CANCELLED`、権限表、処理順)と **D-5: P2-08 §4 / P2-09 §5 のG-09再改訂**を追加(現在の D-1〜D-3 にどちらも入っていません — X-4/X-5参照)

  - §7の作業分割へ取消の作業を明示(X-6)
  - 規模「M」の再見積り(テンプレート改修+本番アプリのフィールド追加+権限変更+UI+ポーラー)

いずれにせよ、**「取消を含んだままFROZEN」は、P2-01を暗黙に改訂したまま凍結することになる**ので避けたいところです。

## 3. 要修正

### X-3. 取消ボタンが`ACCEPTED`の行にも表示され、押しても効かない

§5は取消ボタンを「pending表示箇所(行の『要求処理待ち #id』・ヘッダーの処理待ちSTART一覧)」へ置くとしています。しかし pending の定義は **P2-09 §3共通4 と §5 のガードGETの両方で `state in (REQUESTED, ACCEPTED)`** です。したがって:

- **`ACCEPTED`(claim済み)の要求にも取消ボタンが出る**
- 押すと確認ダイアログが出て、PUTは成功し、しかし**ポーラーは無視して処理を続行する**(§4「ACCEPTED以降のチェックは無視され処理続行」、§5「claim済み要求への取消PUTは無害」)
- 利用者から見ると「取消を押して成功したのにRunが作られた」= **静かに効かなかった操作**

§5は「無害」と書いていますが、無害なのは*システムにとって*であって、*利用者にとって*は誤解を生みます。これはP2-09が2度にわたって規律化した論点そのものです:

- 第2巡指摘2「押しても必ず拒否されるボタンが出る欠陥を**先回りで防ぐ**」
- 第3巡指摘3「**ボタンが出ない行には理由を書く**、で全行統一」

対応:

- 取消ボタンは **`REQUESTED` の行にのみ表示**する(ガードGETは`request_state`を取得済みなので判定材料はある)。
- `ACCEPTED` の行は「**処理中(取消できません)**」を表示(ボタンなし+理由あり — P2-09第3巡指摘3の統一規律どおり)。
- 表示後にclaimされる残存レースは避けられないので、**取消PUT後の表示を定義**する:「取消を受け付けました。すでに処理が始まっている場合は実行されます。結果は要求レコードでご確認ください」。P2-09共通1が「開始と完了を区別する」ためにやったのと同じ手当です。
- あわせて、**取消しても最大5分は pending 表示のまま残る**(次のポーラー周回まで`CANCELLED`にならない)ことを文言に含める。

### X-4. 編集権限は「運用規律」ではなく kintone のフィールドアクセス権で絞る

§5は権限線の変更をこう書いています:

> 一次対応者へ要求アプリの**編集権限**が必要になる(…「追加+取消(ボタン経由)。**他欄の直接編集は禁止**」へ改訂 — 機械欄の誤編集は既存のfail-closedパーサ(個別REJECTED)が防波堤)

ここは2点弱いです。

**(1) fail-closedパーサは「不正な値」を弾けても「正当な値への書き換え」は弾けません。** レコード編集権限があれば、claim前に:

- `network_id` / `business_key` / `scheduled_for` を**別の対象へ書き換える**(作成者フィールドは元のままなので、監査上は「Aさんが最初に書いた内容」に見えるが実際は別の起動)
- `reason` を事後に書き換える(要求レコード自体が監査であるというP2-01 §3の前提が崩れる)
- `request_state` を `REJECTED` → `REQUESTED` へ戻して**再処理させる**(受理範囲の迂回路)

いずれも「正当な値」なのでパーサは通します。P2-01 §3が「人が書くのは操作要求アプリのみ、そこへ機械が状態を書き戻す」「作成者=要求者の真正性の根拠(偽装不可)」と設計した分離が、編集権限の付与で緩みます。

**(2) kintoneには製品機能としてフィールド単位のアクセス権があります。** 運用規律に頼る必要がなく、`cancel_requested` **以外の全フィールドを一次対応者ロールに対して編集不可**に設定すれば、上記はすべて設定で塞げます(レコード編集権限は付与しつつ、編集できる欄を1つに限定する)。

→ §5の権限線の記述を「運用規律+パーサ」から「**フィールドアクセス権で`cancel_requested`のみ編集可(人間欄・機械欄とも編集不可)**」へ書き換え、テンプレートのConsoleスクリプト側でこの設定を作るところまでM1に含めてください。受入にも「他欄が編集できないこと」を1行(設定の回帰を防ぐ)。

### X-5. G-09境界の再改訂が M0 の改訂リストに入っていない

§5は「**G-09境界の変更**: 要求アプリへの書込みは『単票POST+`cancel_requested`欄のみの単票PUT』となる」と書いています。しかしG-09の正本は P2-08 §4 で、それを P2-09 §5 が「**書込は操作要求アプリへのレコードPOSTのみ**(cursor・Bulk・PUT/DELETEは引き続き禁止)」へ改訂したものです。**PUTは明示的に禁止されている側**にあります。

§7 M0の改訂リストは D-1(P2-08計画§9撤回)/ D-2(P2-01 G-03)/ D-3(P2-09 §3) のみで、**G-09本体(P2-08 §4)と P2-09 §5・P2-09受入9(「実行管理・監査へのPOST/PUT/DELETEがない」)の再改訂が入っていません**。第1回レビューのD-1〜D-3と同じ性質の漏れです。

→ **D-4: P2-08 §4 G-09 と P2-09 §5・受入9 を「操作要求アプリへの単票POST+`cancel_requested`欄のみの単票PUT」へ再改訂**をM0リストへ。X-1で(b)内包を選ぶ場合は **D-5: P2-01 §3/§4/§5** も併せて。

### X-6. §7の作業分割表に取消の作業が1つも無い

§3・§4・§5・受入8に取消の仕様があるのに、作業表(M1〜M4)には対応する作業がありません:

| 作業 | 現在の記載 | 欠けているもの |
| --- | --- | --- |
| M1 | 「START種別+3欄追補、request-model検証、allowlist`app_start`」 | `cancel_requested`欄、`request_state`への`CANCELLED`選択肢追加、**フィールドアクセス権設定**(X-4) |
| M2 | 「START処理(…)、`blocked_run_ids`、単体=matrix全行+argv+安全取り出し」 | **claim時の`cancel_requested`検知と`CANCELLED`遷移**、その単体 |
| M4 | 「新規実行ボタン・入力モード切替・処理待ちSTART表示・受入5・7」 | **取消ボタン・確認ダイアログ・取消欄のみPUT** |

M0のチェック項目「仕様条件追加=受入同時追加」(P2-09の教訓)の**逆方向** — 受入は追加されたが作業が追加されていない — です。同じチェック項目に「受入追加=作業分割へ同時反映」を足しておくと、次から機械的に拾えます。

### X-7. M0のコード確認は3点ではなく4点(NOOP経路の`run_id`)

§2はNOOPについてこう書いています:

> **NOOP経路のJSON `run_id`=既存SUCCESS Runのidである契約を明文化**(…現行G-04のNOOP出力仕様どおり。固定文言の`既存Run #<id>`はここから取得)

しかしP2-01 G-04の記述は「`outcome / run_id / invocation_id / aggregate_status / invocation_result_code / retry_brake_node_ids`。**NO-OPは`invocation_id = null`**、`retry_brake_node_ids = []`」であり、**NO-OP時に`run_id`へ既存Runのidが入るとは明示されていません**(nullになる余地がある)。§9も「実装変更は不要**見込み**」としています。

§4のNOOP固定文言は`既存Run #<id>`を必須にしているので、**これが載らなければ受入3が成立しません**。第2回レビューのN-3(「見込み」で受入をブロックしている)と同じ構図です。M0のコード確認へ **④NOOP経路の`--json`に既存Run idが載るか** を追加してください(①〜③と同じ場所を読むついでに確認できます)。

## 4. 軽微

- **Y-1. 取消の排他根拠を明文化する。** 取消PUTと claim(`ACCEPTED`へのPUT)のレースは、**取消PUTがrevisionを進めるため、P2-01 §5のrevision fencingでclaimが必ず競合して弾かれ、次周回で`CANCELLED`へ落ちる**、という形で安全側に倒れます。これは実装依存の性質(claimのfencingがGET時のrevisionを使うこと)なので、§3か§4へ1行書いておかないと、実装者が「claim後に別GETで`cancel_requested`を読む」形にしてウィンドウを作り得ます。同時に、**弾かれた分は次周回まで待つので取消の反映に最大5分かかる**ことも文言へ(X-3の表示と対)。
- **Y-2. `explicit` policy に `scheduled_for` を許さないのは、N-1と同じ穴を将来に残します。** Phase 1 §9のas_of規則は policy と独立に `--scheduled-for` の有無で決まるので、explicit network に `business_key` + `scheduled_for` を渡すのは意味論的に矛盾しません(キーは明示、as-ofは固定)。現在explicit networkは存在しないので実害はありませんが、最初のexplicit networkでバックフィルをやろうとした瞬間にN-1と同型の「静かに間違う」を踏みます。§3表へ「explicitでas-of固定が必要になった場合は再審議」の1行を。
- **Y-3. `MAX_ACTIVE_RUNS` と `LOCK_CONFLICT` は利用者から見ると同じ状況の別表示です**(Phase 1 §9のとおりロック取得後にmax判定なので、実行中ならLOCK_CONFLICT、未完了で停止中ならMAX_ACTIVE_RUNS)。挙動は正しいのですが案内文が違う(「時間をおいて再起票」vs「RERUNを」)ので、一次対応1ページでは「**どちらも未完了Runが1本あることが原因**」と束ねて説明すると迷いません。
- **Y-4(N-7継続). ゲート③(全ノード冪等)の判定と、実際に走るbundleの版がずれうる**問題は未対応のままです。「定義のデプロイ中はポーラーを停止する / allowlist編集とデプロイの順序を固定する」の運用注記を§8へ。
- **Y-5(N-8継続). 候補①のラベル**「START DONE実績」の`DONE`には`NOOP_ALREADY_SUCCESS`(=起動していない)が含まれます。「START要求実績」等が正確。
- **Y-6(N-9継続). FROZENの完了条件が未定義。** 「DRAFT v5(FROZEN候補)」の次に何が起きればFROZENなのか(M0のコード確認4点の完了+改訂リスト反映+Codexレビュー通過、など)を§7 M0へ1行。
- **Y-7. 受入3「ほぼ同時2件で1件のみ作成」の敗者側の理由コードが未定義。** ensure-runの重複禁止INSERTで敗れた側がどのコードで`REJECTED`になるか(同一キー未完了と同じ`blocked_run_ids`経路か、別コードか)を決めておくと単体が書けます。matrixにも行がありません。
