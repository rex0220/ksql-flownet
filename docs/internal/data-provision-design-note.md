# 他システムへのデータ提供 — FlowNet における理想形(設計メモ)

- 作成: 2026-09-02 / 状態: **検討メモ(決定ではない)**

- 突合先: `job-network-phase1-spec.md` §2.1・§4.2・§7.1・§10・§22相当、`execution-contract-v1.md` §11、`architecture-separation-adr.md` §7、`ksql-flownet-vision.md` §2

---

## 0. 結論

**push しない。kintone アプリを提供面にして相手に pull させ、DAG の最終ノードで「公開マーカー」を立てる。**

これは前回整理したパターンA(SQL副作用)/B(executor拡張)/C(外部観測ワーカー)のいずれでもない**第4の道**であり、3つの中で最も安いどころか、**FlowNet に一切の拡張を要求しません**。提供処理が SQL の `UPSERT` だけで書けるため、ノードは全て冪等のまま、Execution Contract も executor も無改修で済みます。

---

## 1. なぜ push ではないのか

外部へ送る(HTTP POST / SFTP / S3 / ファイル出力)形はすべて**非冪等な副作用**です。Phase 1 §4.2 が「外部への通知は完全に決定的でも非冪等」と名指しする類型そのもので、以下が同時に発生します。

- resume(§7.1)で `FAILED` の冪等ノードが `WAITING` へ戻る → **再送**
- kSQL-Flow 内部の chunk リトライ → **再送**
- 送信結果が確定できないと `UNKNOWN` → 「送ったか分からない」状態が業務に残る
- secret(相手の認証情報)を FlowNet が保持することになる → ADR §7 の前提(secret 受渡し・sandbox)に抵触
- Execution Contract §11「snapshot は外部 API 応答を固定しない」→ 再現性の外へ出る

つまり push を選んだ瞬間に、このプロジェクトが積み上げた保証のほぼ全部を手放します。

**pull なら、これが全部消えます。** 提供とは「相手が読める場所にデータを置くこと」であり、置く操作は `UPSERT` = 冪等。送信という非冪等操作が設計から消滅します。

---

## 2. 全体像

```
[業務アプリ群] ──SQLノード──▶ [提供アプリ(データマート)]  ← 相手システムが閲覧トークンで pull
                                      ▲
                              publishノード(最終)
                                      │
                              [公開マーカー]  ← 相手はまずここを読む
```

- **提供アプリ**: 業務アプリでも実行管理アプリでもない**第3の場所**。機械(FlowNet)が書き、外部が読む
- **公開マーカー**: 「この業務キーの版は読んでよい」という唯一の宣言。DAG の最終ノードが立てる

---

## 3. 設計要素

### 3-1. 提供面は専用の kintone アプリに切る

業務アプリを直接読ませない。理由:

| 理由 | 効果 |
| --- | --- |
| アクセス境界 | 閲覧のみの API トークンを**アプリ単位**で発行できる。生データを触らせない |
| 契約の隔離 | 業務アプリのスキーマ変更が、相手との提供契約に直接波及しない |
| 射影の固定 | 渡す列だけを持つ。個人情報等を構造的に排除できる |
| 量の管理 | レコード上限・保持期間を提供側で独立に決められる |

FlowNet が書き、外部が読む — 人は書かない。vision §2 の「人が書く場所と機械が書く場所を必ず分ける」設計制約の、そのままの延長です。

### 3-2. 版は business key で持つ(上書きしない)

提供レコードは `business_key`(`monthly_deal_summary@2026-08`)を持ち、**版ごとに別レコード群として積む**。既存レコードを上書きしません。

- **UPSERT キー = `business_key` + 明細キー** → リランしても同じ内容に収束する(冪等)
- 補正 Run(`…-correction-1`)は別 business key なので、**別の版として並存**する。Phase 1 §2.1 の業務キー設計がそのまま提供の版管理になる
- 上書き方式を採らないのは、**書き込み途中の状態を相手が読む可能性を消す**ため。追記 + ポインタ切替(blue/green)にすることで、相手は常に完成した版だけを見る

### 3-3. 公開マーカー — 「業務の完了」の唯一の外部向け宣言

DAG の末端に `publish` ノードを置き、提供の状態レコードを `READY` にします。

| 項目 | 意味 |
| --- | --- |
| `business_key` | どの業務単位の版か |
| `run_id` | 生成した Run(監査で遡れる) |
| `as_of` | どの時点の断面か(Phase 1 §9 で Run に固定済みの値) |
| `schema_version` | 提供スキーマの版(相手との契約) |
| `record_count` / 合計値 | 相手が自己検証するための材料 |
| `published_at` / `status` | `READY` / `WITHDRAWN` |
| `supersedes` | 前版の business key(補正で置き換えた場合) |

相手システムの作法は「**マーカーを読み、`READY` を確認してから明細を取りに来る**」。これで読み取り側が fail-closed になります。

**これが前回議論した「DAG の完走 ≠ 業務の完了」への直接の答えです。** マーカーが立つことが業務の完了の定義になり、両者が一致します。

### 3-4. トランザクションが無いシステムで一貫した読み取りを与える唯一の方法

kSQL にトランザクションはありません(kintone API の制約)。したがって「途中まで書けた状態」は原理的に発生します。**それでも相手に一貫した読み取りを保証できるのは、「全データを書き終えてから最後にマーカーを立てる」順序だけです。**

そしてその順序を機械的に保証するのが、まさに FlowNet の仕事です — 安定トポロジカル順の直列実行と `trigger_rule: all_success`(全上流が `SUCCESS` のときだけ着手)。**データ提供は DAG の拡張機能ではなく、DAG の本来用途にきれいに乗る**、というのがこの設計の一番おいしい点です。

### 3-5. 失敗時の挙動(自動的に安全側)

| 事象 | 相手から見えるもの |
| --- | --- |
| 途中ノードが `FAILED` | マーカーが立たない → **前版を読み続ける**(古いが一貫したデータ) |
| ノードが `UNKNOWN` | 同上。§7.1 により後続(publish)は着手されない |
| Run が `CANCELLED`(STOP) | 同上 |
| リラン完走 | 新版のマーカーが立ち、相手は次のポーリングで切り替わる |

**「不完全なデータを見せる」経路が構造的に存在しません。** 見えるのは常に「完成した最新版」か「完成した前版」のどちらかです。

### 3-6. P2-11(START)との相性

publish ノードを含む全ノードが `UPSERT` = 冪等なので、**三重ゲート③(全ノードが明示的に `idempotent: true`)を満たしたまま**です。したがって:

- allowlist に `app_start: true` を付ければ、**補正版の再公開を kintone のボードから起動できる**
- correction START のキー規則(`business_key` + `scheduled_for` 両方指定・as-of は対象期間)がそのまま「8月分を再集計して新版として公開する」操作になる

push 方式だと非冪等ノードが混じるため、この経路は永久に閉じたままになります。ここは設計選択の効き方として大きい差です。

### 3-7. 通知が必要な場合

相手がポーリングできない場合に限り、**通知だけを FlowNet の外に置く**(パターンC = 外部観測ワーカー、または kintone の Webhook / 通知機能)。

この分離が成立するのは、**通知が失敗しても業務は完了しているから**です。データ提供の正はマーカーであって通知ではありません。通知が重複しても、相手が取りに来る先が冪等なので実害がありません。「通知は best-effort、正はマーカー」と明記すること。

外部観測ワーカーを書く場合、**実行管理・監査アプリは GET 限定**(G-09)という制約に注意。ただしこの用途では**提供アプリのマーカーを読めば足りる**ので、そもそも実行管理アプリを見る必要がありません — 相手にも自前ワーカーにも、機械専用アプリを一切開示せずに済みます。

### 3-8. ファイル(CSV)で渡す必要がある場合

提供アプリの内容を cli-kintone または kSQL の出力機能で取り出します。**FlowNet のノードにはしない。** ファイル生成を DAG の順序に組み込みたくなったら、それが executor 拡張(パターンB)の着手条件の1件目です。

## 4. この設計が満たすもの

| 観点 | 結果 |
| --- | --- |
| Execution Contract v1 | **無改修** |
| executor 拡張 | **不要**(SQL の UPSERT だけで書ける) |
| 冪等性 | 全ノード冪等。リラン・chunk リトライで壊れない |
| secret | FlowNet は相手の認証情報を持たない(kintone の閲覧トークンを相手が持つ) |
| as-of | Run に固定された値がマーカーに刻まれ、「いつ時点のデータか」が提供物に載る |
| 機械専用制約 | 維持(提供アプリも機械が書き、人は書かない) |
| 失敗時 | fail-closed(前版が残る)。不完全な読み取りが構造的に発生しない |
| P2-11 START | 使える(補正版の再公開をアプリから起動可能) |
| 監査 | マーカーの `run_id` から Run・Invocation・Attempt・JOB ログまで既存の相関で遡れる |

## 5. 弱点とトレードオフ(正直な整理)

- **リアルタイム性がない。** pull + ポーリングなので、相手のポーリング間隔ぶんの遅延が乗る。秒単位の連携には向かない
- **量の上限は kintone の API 制約が決める。** 件数・レートが提供規模の天井。大量データの提供基盤にはならない
- **相手に作法を要求する。** 「マーカーを見てから明細を読む」という統合契約が発生し、文書化と相手側の実装が要る。ここを守ってもらえないと保証が崩れる
- **スキーマ変更が契約変更になる。** `schema_version` を最初から持たせ、旧版との併走期間を設計に入れておくこと
- **保持期間の設計が要る。** 版を積む方式なので、古い版の削除ポリシー(何版残すか / 何か月か)を決めないとレコードが増え続ける
- **相手が複数になると射影も複数要る。** 提供アプリを相手ごとに分けるか、1アプリで列を絞った閲覧権限にするかの判断が要る(前者を推奨 — 契約の独立性が保てる)

---

## 6. 次に決めること(着手する場合)

1. 提供アプリのテンプレート(マーカー + 明細の 2 レコード種別 or 2 アプリ構成のどちらにするか)
2. マーカーのフィールド定義と `status` の値集合(`READY` / `WITHDRAWN`)
3. 版の保持ポリシーと削除の担い手(DAG の末端ノードで古い版を DELETE するか、運用で回すか)
4. 相手向けの統合仕様書(マーカーの読み方・自己検証手順・`schema_version` の互換規約)
5. 最初の1件で実機検証(実機ゲート主義): 途中失敗させて**前版が読み続けられること**を証跡に残す
