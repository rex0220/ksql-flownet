## 0. 結論

| 実装場所 | 評価 |
| --- | --- |
| (a) 新しい executor 種別として CSV 出力ノードを作る | **不要**。(c)で足りる |
| (b) **FlowNet 本体**(orchestrator / `run-network`)に CSV 出力を足す | **却下**。Execution Contract §10「FlowNet は業務データを持たない」を壊す(§2) |
| (c) **kSQL-Flow の CLI オプション**として足す | **見かけ倒し**。実体は **kSQL(engine / 言語)への追加**であり、コストは小さくない(§3) |
| (d) **どこにも足さず、配信アダプタの中で cli-kintone を使う** | **推奨**(§5) |

**CSV 出力は「シリアライズ機能」ではなく「値表現の対外契約」です。** 一度出した表現は相手のシステムに固定され、kSQL のバージョン間で変えられなくなります。そして大量出力という本来の目的に対しては、現在の engine がストリーミングを持たないため、CSV シリアライズより**メモリモデルの変更が本体**になります。

cli-kintone はこの契約(Shift_JIS、サブテーブル `*` 形式、添付ファイル、ヘッダ=フィールドコード)を**既に全部持っています**。R12 が cli-kintone を round-trip の相手として公式に位置づけているのは、出力側の契約が既に世の中にあるからです。**第2の CSV 方言を作る意味は薄い。**

## 1. v1 からの訂正

**訂正A(v1 §1 の訂正はそのまま有効)**: 「ファイル出力は通知と同類の非冪等操作」は誤り。①同一パスへ全量上書き ②一時ファイル+rename ③as-of が Run に固定、の3条件で **CSV 出力は冪等**。Phase 1 §4.2 が挙げる非冪等の例(キー指定のない INSERT / 外部への通知)のどちらでもない。

**訂正B(v1 §1)**: 「CSV/TSV/JSON 出力は既存 executor の出力形式追加であり executor 拡張ではない」— これは**カテゴリの話としては正しいが、コストの話としては誤解を招いた**。executor 拡張(任意コード実行)ではないが、**engine への追加**であって「小」ではない(§3)。

**訂正C(v1 §5 — これが本題)**: 「kSQL-Flow: SELECT 結果の CSV シリアライズ = **小**」は**誤り**。追加先は kSQL-Flow ではなく **kSQL(engine / 言語)**であり、規模は **中〜大**。理由を §3 に記す。

## 2. (b) FlowNet 本体に足すのが却下である理由(v1 から変更なし)

FlowNet は業務データを一度も見ない設計で、これは契約で明示的に禁止されています。

Execution Contract §10:
> **stdout JSON に顧客レコードの内容を含めない。**

ADR §4 の実行境界でも、kSQL-Flow が FlowNet へ返すのは `JSON result + exit code`(status / resultCode / 件数 / version / as-of)であってレコードそのものではありません。CSV を FlowNet に通せば、Execution Result のサイズが業務データ量に比例し、監査履歴アプリに個人情報が載りうるようになり、§10 の規律を全面的に見直すことになります。**データを持っているのは kSQL-Flow 側**なので、そこで書けば済む話です。

---

## 3. (c) が「kSQL-Flow への追加」ではなく「kSQL への追加」である理由

`--out-csv <path>` という CLI オプションの見た目に反して、決めなければならないことのほぼ全部が **engine の値表現の決定**です。

### 3-1. 型ごとの表現を決める = 言語の対外契約が1つ増える

| 決めること | なぜ engine の領分か |
| --- | --- |
| **数値** | 「取得した数値そのものは文字列のまま保持するため、算術を通さなければ桁落ちしない」(§22)。裏返すと**算術を通った列は IEEE 754 の誤差がそのまま出る**(`3000 * 1.1` → `3300.0000000000005`)。§22 は「結果を `UPDATE SET` や一時テーブル経由で保存すると、その差が保存データへ残る」と警告しているが、**CSV に出すとその差が社外のシステムへ流れて固定される**。丸め方針を engine が決める必要がある |
| **空セル / NULL** | 算術では「空セル = 0 扱い」(§22)。出力では空文字か、`0` か、区別するのか |
| **日付・日時** | kintone は UTC 保持、network の timezone は Asia/Tokyo。どちらで書くか、offset を付けるか |
| **複数値フィールド** | チェックボックス・ユーザー選択のセル内表現。R12 が cli-kintone 互換で「複数値はセル内 LF」としており、**ここを揃えないと第2の方言が生まれる** |
| **サブテーブル** | R12 の CSV `*` 形式(cli-kintone export 形式)を再現するのか。親子の行展開規則は engine の話 |
| **Shift_JIS** | R8 の変換資産はあるが、出力できない漢字を置換するのかエラーにするのかは方針決定 |

### 3-2. 列名の小文字正規化が round-trip を壊す

言語リファレンス §1:
> SELECT 列別名の英字(全角を含む)は結果列名で**小文字へ正規化されます**。バッククォートで囲んでも結果列名の大文字・小文字は保持されません。

つまり素直に CSV ヘッダを出すと、**kintone のフィールドコードと大文字小文字が一致しません**。R12 の `IMPORT ... FROM CSV exported BY NAME`(ヘッダ=フィールドコード名で対応)と対称にならず、**自分で出した CSV を自分で取り込めない**という事態が起こります。日本語フィールドコードなら顕在化しませんが、ASCII コードを使うアプリ(システム連携用途に多い)で必ず踏みます。

回避するには「出力時はヘッダの大小を保持する」という**言語規則の例外**を作ることになり、engine の識別子正規化に手を入れる話になります。

### 3-3. 量が理由なのに、その量域で engine が持たない

これが v1 の最大の自己矛盾でした。「量が理由なら CSV」と書きましたが、**まさにその量域が現在の engine の外**です。

- 取得件数上限: engine 既定 **10,000 件** / CLI 既定 500 件(§22)
- R7 の Cursor API(v3.1.0)で大窓は取れるが、**「OFFSET 分を kSQL が受信して読み捨てる」**方式であり、走査件数 `OFFSET + LIMIT` ≤ 実行時 `maxRecords` が条件。つまり**全件をメモリに載せる**
- FULL_SCAN モードは JS 側で結果配列を持つ(JOIN / GROUP BY / DISTINCT / UNION / ウィンドウ関数はすべて FULL_SCAN)

数万〜十万件の CSV を毎月出すには、**取得と出力をパイプライン化するストリーミング出力**が要ります。それは engine のメモリモデルの変更であって、CSV シリアライズはその上に乗る薄い層にすぎません。**本体はストリーミング化のほうです。**

### 3-4. 後方互換の重荷が増える

一度リリースした CSV の値表現は、相手システムが依存するため**kSQL のバージョン間で変えられなくなります**。ADR §8 が分離の利点に挙げた「kSQL-Flow の既存利用者と**軽量性**を維持できる」と正面から衝突します。「SQL 専用に絞ることで軽さと防御力を保つ」という方針そのものへの負荷です。

## 4. どうしても足すなら(条件と最小形)

(c) を選ぶ場合の設計自体は v1 のままで妥当です。要点のみ再掲します。

- `ksql-flow run … --out-csv <path> --out-encoding utf8|sjis`。**FlowNet が絶対パスを組み立てて渡す**。SQL はパスを持たない(IMPORT の `--import-csv name=path` = off-by-default と対称)
- Contract **v1.1** として capability negotiation(§9)へ `"resultCsv": true` を追加。capability は Run snapshot に保存されるので、出力できない版での resume も防げる
- 出力先は allowlist されたディレクトリ配下のみ。ファイル名は `business_key` と node id から決定的に生成。一時ファイル + rename
- Execution Result へ **`output_files: [{name, sha256, rows, bytes, encoding}]`** を記録。名前は §10 どおり秘密情報を含まない相対表示名へ正規化。**FlowNet はレコードを1件も持たないまま「何を出したか」の同一性を監査でき**、ハッシュはリランの冪等性の実測手段にもなる
- **マーカーは kintone に残す**。CSV を書いた直後に失敗すると未完成ファイルがディスクに残るため、「いつ配信してよいか」の宣言は別に必要。publish ノードは SQL のままなので三重ゲート③も P2-11 の START も維持される

構成は提供アプリ方式と同じ骨格で、**明細の置き場所だけが kintone → ファイル**に変わります。

## 5. 推奨 — (d) 配信アダプタの中で cli-kintone を使う

大量 CSV が必要になった場合の最も安い解です。

```
[SQLノード群] → 提供アプリ(または業務アプリ)へ UPSERT
       ↓
  publishノード(最終・SQL) → [マーカー]  ← 配信アダプタが読む
                                   ↓
                        配信アダプタ(FlowNetの外・cron)
                          └ cli-kintone で export → 相手へ送る
```

- **cli-kintone は値表現契約を既に持っている**。Shift_JIS、サブテーブル `*` 形式、添付ファイル、ヘッダ=フィールドコード。kSQL 側で同じものを再発明しない
- **cli-kintone をノードにはしない**(Execution Contract 非準拠 / Node ロックキーが作れない / secret と bundle が未定義 — 前回の3障害)。しかし**配信アダプタの中でなら何を使っても自由**。ここは FlowNet の管轄外
- 配信アダプタは P2-01 のポーラーと同型(one-shot cron・状態は kintone・revision fencing・fail-closed)。**既に一度作って実機で通した型の再利用**
- マーカーだけ FlowNet が SQL で立てる。**engine にも Contract にも一切触らない**

トレードオフは、提供アプリへ一度書く分の kintone API 呼び出しが増えること。ここが効くのは §3-3 の量域(数万件〜)で、その場合は業務アプリから cli-kintone が直接 export し、**マーカーだけを FlowNet が立てる**形にできます(提供アプリを挟まない代わりに、版の再現性は失われる — 量と再現性のトレードオフを明示的に選ぶ)。

## 6. コスト再見積り

| 実装場所 | 規模 | 内訳 |
| --- | --- | --- |
| (b) FlowNet 本体 | — | 却下(§2) |
| (c) kSQL への追加 | **中〜大** | 型別の値表現決定(§3-1)+ 列名正規化の例外(§3-2)+ **ストリーミング出力=メモリモデル変更**(§3-3)+ Contract v1.1 と contract test + 出力先 allowlist + `output_files` + 対外契約としての後方互換責任(§3-4)+ 運用(ディスク・保持期間) |
| (d) 配信アダプタ + cli-kintone | **小** | 提供アプリ・publish ノード・マーカーは CSV の有無に関わらず必要。追加は配信アダプタの中で cli-kintone を呼ぶ部分と、その結果のマーカーへの書き戻し |

## 7. 判断のための問い

1. **提供する件数はいくつか。** 数千件までなら提供アプリだけで完結し、CSV は不要
2. **相手はファイルを要求しているのか、量が理由か。** 前者なら配信アダプタでの変換で足りる
3. **cli-kintone で足りない要件が具体的にあるか。** 「kSQL の変換・検証を通した結果をそのまま出したい」なら、提供アプリへ UPSERT → cli-kintone で export の2段で同じことができる(段が増える代わりに版が kintone に残る)
4. **CSV の値表現を対外契約として維持する覚悟があるか。** これが (c) を選ぶ場合の実質的なコミットメント

1〜3 のいずれかで (d) に落ちるなら、**kSQL には何も足さない**のが正解です。
