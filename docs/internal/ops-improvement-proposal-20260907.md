## 3. 第 1 段階の設計メモ

### 3.1 `doctor`(導入チェックの統合)

- 既存の `validate --check-logapp`、`poll-requests --check`、`capabilities` を 1 コマンドにまとめ、加えて環境変数の存在(名前のみ)、IO ディレクトリの所有者と権限、crontab に起動行があるか、kSQL-Flow と kSQL-FlowNet の版の組合せを確認する
- 検査ごとに **実施状況** と **結果** を分けて出す。実施状況は「実施した / 手動確認が必要(API トークンでは field/acl を読めないため、フィールドアクセス権や人の権限はここ) / 取得に失敗した(通信断・権限不足)」。結果は「正常 / 不適合」。失敗を「未確認」と混ぜない
- 終了コード: すべて正常 = 0、必須検査に不適合または取得失敗がある = 1、任意検査だけに不適合がある = 0 で警告を出力。必須と任意の区分は仕様で列挙する
- 読取専用。状態を書かない

### 3.2 `diagnose`(診断情報の一括出力)

- 対象 Run または network について、`status --json` の内容、Attempt と JOBログの突合結果、ロックと stale 判定、直近の拒否理由、ポーラーの直近周期の要約、双方の版、環境変数名、IO ディレクトリの状態を 1 つの JSON にまとめる
- 秘匿化は **出力項目の許可リスト方式** にする。名前に TOKEN / SECRET / PASSWORD を含む値を伏せる規則だけでは、ログ末尾に含まれる秘密値・SQL 本文・絶対パスを除去できない。生ログは既定で含めず、構造化した時刻・コード・識別子(run_id、attempt_id、request_id、event_id)だけを収集する。生ログが必要なときは別オプションで、人が内容を確認してから渡す
- URL のクエリ・ヘッダー・本文は含めない。SQL 本文は含めない(job_id と bundle sha256 で特定できる)
- 読取専用。二次対応者と問い合わせへの受け渡しが目的

### 3.3 ポーラー heartbeat

- 置き場所は **実行管理アプリ**。操作要求アプリに置くと、claim・件数集計・stale 判定・清掃のすべてで除外契約が要る。実行管理は既に `record_type` で NETWORK_RUN・NODE_STATE・NETWORK_LOCK を同居させており、`POLLER_HEARTBEAT` を足す形は既存の型と同じ。CLI 専用アプリなので人は触らない
- ホストごとに 1 レコード(`record_key` は `HB:` + profile とホスト名のハッシュ、64 文字以内)。同一ホストの重複起動は起動スクリプトの flock で止めている
- 周期ごとに `revision` 付きで更新する。書けなくてもポーラーの本処理は止めない(ベストエフォート。失敗はログに残す)
- **監視対象ホストは設定で明示する**(§3.4 の設定ファイルに `hosts` を列挙)。未作成・廃止・複数ホストの扱い:
  - 設定にあるがレコードがない → 「稼働確認なし」
  - 設定にないレコード(廃止ホスト)→ ボードに出さない。運用で削除する(CLI に `heartbeat --retire <host>` を用意し、監査を残す)
  - 複数ホストが同じ network を評価する構成は取らない。評価の担当は `hosts` に 1 台だけ指定し、他のホストは heartbeat だけを書く
- ボードの表示は原因を言わない。heartbeat は「観測できた最後の稼働」であって原因(VPS 停止・cron 停止・認証失敗・通信断)ではない
- 誰もボードを開かなくても通知する要件は別系統(cron の MAILTO、外部 ping)。本案の範囲外

### 3.4 期待 Run の照合(`expected_by`)

- FDR D-30(cron を内蔵しない)は維持する。**判定するだけで起動しない。** 検知と自動補完は分ける(scheduling-patterns の MANUAL_BACKFILL と同じ考え方)
- 設定は allowlist と **別ファイル**にし、環境変数で指す。allowlist の意味は「誰が何を起動できるか」で、監視設定を混ぜると意味が広がる(「追加は自由、意味変更は重い」)
- 仕様化する項目: タイムゾーン(プロファイルの設定に従う。kintone は分精度なので期限も分単位)、対象期間の導出(**既存の定期実行の業務キー導出規則を再利用する**。補正 Run を定期 Run の代わりに数えるかは別に定義する)、許容遅延(分)、要求する状態(**存在** と **SUCCESS** を別の期限で持てる)
- 評価結果は heartbeat と同じレコードに載せるが、**heartbeat の更新成功と評価の成功は別のフィールドで持つ**: `heartbeat_at`、`evaluation_status`(OK / FAILED と失敗コード)、`last_successful_evaluated_at`、未実行・未完了・遅延完了の一覧。照合に失敗した周期は `heartbeat_at` だけを進め、一覧と `last_successful_evaluated_at` は前回のまま残し、`evaluation_status = FAILED` を書く
- 「期限までに SUCCESS」の判定は Run の完了時刻(Node State の最終更新か Attempt の `finished_at`)で行う。信頼できる完了時刻がない場合(UNKNOWN の裁定後など)は期限内完了と断定せず「未完了(完了時刻不明)」にする

監視結果の表示は次の 6 状態に分ける。

| 状況 | 表示 |
| --- | --- |
| heartbeat レコード未作成(設定にあるホスト) | 稼働確認なし |
| heartbeat が古い | ポーラー稼働確認が途絶 |
| heartbeat は新しいが照合失敗(`evaluation_status = FAILED`) | ポーラー稼働確認済み・期待 Run の判定不能(前回の一覧を参考情報として表示) |
| 照合成功、期限超過、Run なし | 未実行 |
| 照合成功、完了期限超過、未成功 | 未完了 |
| 期限超過後に成功 | 遅延完了(期限超過の履歴を残す) |

受入条件: **最新の照合失敗を前回の正常結果で覆わない。** 前回の結果は参考情報として表示してよいが、判定として表示しない。

## 4. 第 2 段階の設計メモ

### 4.1 版別配置と切替

1. 指定したコミットを新しい版別ディレクトリへ取得する(`git status --porcelain` が空でなければ止める。dirty な作業ツリーではコミット ID で内容を特定できない)
2. そのディレクトリで `validate` と `plan` を実行する
3. 合格したら、新規実行が参照する `current` の参照先を切り替える
4. 失敗したら現在の配置先を維持する

契約:

- **起動と切替は共通の配置ロックで調整する。** 起動スクリプトと配置スクリプトが同じ flock を取り、切替中の起動と起動中の切替を排他する。シンボリックリンクの原子的な差し替えだけでは、起動側が複数ファイルを読む間の一貫性を固定できない
- **起動時に実体ディレクトリを一度だけ解決し、その実行中は固定する。** 起動スクリプトは `current` を `readlink -f` で解決した実パスを cwd と引数に使い、以後 `current` を参照しない
- **旧版のディレクトリは実行中の Run がある間は消さない。** NEW の bundle は添付に固定されるが、実行中のプロセスは旧ディレクトリのファイルを参照している。保持世代数を決めて古いものだけ消す
- kSQL-Flow のローカルロックは cwd 単位なので、版別ディレクトリではローカルロックの場所が版ごとに変わる。新旧版の同時起動は分散ロックに頼らず、上の配置ロックで配置側が防ぐ

### 4.2 Run の版表示

- 実行内容の識別は **bundle の sha256**(既に Run に残る)。Git のコミット ID は **由来情報** として追加で残し、ボードに両方を表示する
- 「公開版を更新しても既存 Run の resume 内容が変わらない」は、bundle が NEW 時に添付として固定される現在の設計で既に保証されている。新機能の受入条件にはしない

### 4.3 ボードの対応案内

- 結果コードごとに「次の操作 / 担当区分(一次・二次・サーバー担当) / 必要な証拠」を表示する。正本は一次対応者向け手順書と復旧 runbook。プラグインの文面追加のみで、状態機械と権限は変えない

## 5. SQL ジョブのアプリ管理を採らない理由と再審議条件

- **正本の二重化**: Git を正本にするとアプリは配布キャッシュでしかなく、§4.1 の配置で同じ効果が出る。アプリを正本にすると、現在の Git 中心の仕組み(差分レビュー、履歴、CI の静的検査)をそのまま利用できず、連携か代替の設計が必要になる
- **権限境界**: SQL は業務アプリへ書き込む。SQL アプリを編集できる人は、書込トークンを持つサーバーで動く内容を変えられる。allowlist の `app_start` を「人が名指しした network だけ」に限定した境界を、SQL アプリの ACL・承認者分離・ハッシュ照合で作り直す必要がある
- **既に成り立っているもの**: 既存 Run の SQL 固定は bundle で保証済み

再審議条件: **「Git を扱えない担当者が SQL の変更・承認を担う」という要件が確定したとき。** その場合は最初から、SQL アプリのトークンをサーバー側で読取専用にする、承認者を編集者と別ユーザーにする、承認レコードにハッシュを持たせる、NEW 時にハッシュ不一致なら拒否する、までを含めて仕様化する。

## 6. 効果と測定

効果は定常作業より例外対応(導入・更新・配置変更・障害・担当交代)に現れる。日次 1 本・月次 2 本のように処理が少なく安定している環境では、通常月の削減時間は限定的で、SQL の業務要件整理・開発、原因分析、業務データの補正判断は引き続き人の専門性が要る。改善機能自体の保守工数は新たに発生する。したがって「何割削減」とは言わず、 **追加機能の保守工数を含めて年間の総作業時間が減るか** を測る。

| 測定対象 | 改善前後で同じ条件にするもの |
| --- | --- |
| 導入確認時間 | 同じ設定不備を含む検証環境 |
| 異常発見までの時間 | cron 停止、Run 未作成、照合の通信失敗 |
| 引継ぎ時間 | 異常発見から必要情報が保守担当へ揃うまで |
| 配置・切戻し時間 | 同じ変更と検証失敗 |
| 副担当の復旧 | 同じ障害、主担当の口頭支援なし |
| 年間相当の保守負担 | 新機能の設定・更新・問い合わせも含む |

- 第 1 段階に入る前に「日次 1 本・月次 2 本」のモデル環境を決め、改善前の値を測る(ビジョン §8「測定してから作る」)
- 「副担当の復旧」は本番障害を待たない。m6-04 の強制解放ドリルと同じ形で、副担当が runbook だけを見て検証環境で復旧する訓練を第 3 段階の受入にする
- 削減額は断定しない
