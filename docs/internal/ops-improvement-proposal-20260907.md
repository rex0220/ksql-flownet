# 運用改善案: 診断・見える化、配置の簡素化、保守の標準化

- 文書状態: **案**(討論の結論。決定ではない。実装計画への起票は合意後)
- 作成日: 2026-09-07
- 経緯: ChatGPT の改善提案(SQL ジョブのアプリ管理を P1 とする 8 テーマ案)を、担当 Claude Code が正本(FDR、統合仕様書、実装計画の backlog、ビジョン文書の進め方の原則)と突き合わせて討論し、2 巡で合意した内容をまとめた

## 3. 第 1 段階の設計メモ

### 3.1 `doctor`(導入チェックの統合)

- 既存の `validate --check-logapp`、`poll-requests --check`、`capabilities` を 1 コマンドにまとめ、加えて環境変数の存在(名前のみ)、IO ディレクトリの所有者と権限、crontab に起動行があるか、kSQL-Flow と kSQL-FlowNet の版の組合せを確認する
- 出力は 3 区分を明示する: **確認できた** / **手動確認が必要**(API トークンでは field/acl を読めないため、フィールドアクセス権や人の権限はここ) / **取得に失敗した**(通信断・権限不足)。失敗を「未確認」と混ぜない
- 読取専用。状態を書かない

### 3.2 `diagnose`(診断情報の一括出力)

- 対象 Run または network について、`status --json` の内容、Attempt と JOBログの突合結果、ロックと stale 判定、直近の拒否理由、ポーラーのログ末尾、双方の版、環境変数名、IO ディレクトリの状態を 1 つの JSON にまとめる
- 秘匿化は E2E の結果 JSON と同じ規則(名前に TOKEN / SECRET / PASSWORD を含む値を伏せる)。URL のクエリ・ヘッダー・本文は含めない
- 読取専用。二次対応者と問い合わせへの受け渡しが目的

### 3.3 ポーラー heartbeat

- 置き場所は **実行管理アプリ**。操作要求アプリに置くと、claim・件数集計・stale 判定・清掃のすべてで除外契約が要る。実行管理は既に `record_type` で NETWORK_RUN・NODE_STATE・NETWORK_LOCK を同居させており、`POLLER_HEARTBEAT` を足す形は既存の型と同じ。CLI 専用アプリなので人は触らない
- ホストごとに 1 レコード(`record_key` は `HB:` + profile とホスト名のハッシュ、64 文字以内)。複数ホストの競合は起きない。同一ホストの重複起動は起動スクリプトの flock で止めている
- 周期ごとに `revision` 付きで更新する。書けなくてもポーラーの本処理は止めない(heartbeat はベストエフォート、ただし失敗はログに残す)
- ボードの表示は **「ポーラー最終成功更新から N 分。状態確認が必要」** とし、原因(VPS 停止・cron 停止・認証失敗・通信断)は言わない。heartbeat は「観測できた最後の稼働」であって原因ではない
- 誰もボードを開かなくても通知する要件は別系統(cron の MAILTO、外部 ping)。本案の範囲外

### 3.4 期待 Run の照合(`expected_by`)

- FDR D-30(cron を内蔵しない)は維持する。**判定するだけで起動しない。** 検知と自動補完は分ける(scheduling-patterns の MANUAL_BACKFILL と同じ考え方)
- 設定は allowlist と **別ファイル**にし、環境変数で指す。allowlist の意味は「誰が何を起動できるか」で、監視設定を混ぜると意味が広がる(「追加は自由、意味変更は重い」)
- 仕様化する項目: タイムゾーン(プロファイルの設定に従う。kintone は分精度なので期限も分単位)、対象期間の導出(START の補正モードと同じ `{network_id}@{YYYY-MM}` などの規則を使い、新しい規則を作らない)、許容遅延(分)、要求する状態(**存在** と **SUCCESS** を別の期限で持てる)
- 評価結果(評価時刻、未実行・未完了の一覧)は **heartbeat と同じレコードに載せる**。評価プロセスが止まると新しい判定を書けないため、評価時刻を判定に含める

| 状況 | 判定の根拠 | 表示 |
| --- | --- | --- |
| 未実行 | 評価時刻が新しく、期限超過で Run なし | 未実行 |
| 未完了 | 評価時刻が新しく、Run はあるが期限までに SUCCESS でない | 未完了 |
| 監視情報が古い | 評価時刻(= heartbeat)が閾値より古い | 一覧は表示し「現在の判定不能」を付ける。前回の正常判定を表示し続けない |

## 4. 第 2 段階の設計メモ

### 4.1 版別配置と切替

1. 指定したコミットを新しい版別ディレクトリへ取得する(`git status --porcelain` が空でなければ止める。dirty な作業ツリーではコミット ID で内容を特定できない)
2. そのディレクトリで `validate` と `plan` を実行する
3. 合格したら、新規実行が参照する `current` のシンボリックリンクを差し替える(原子的)
4. 失敗したら現在の配置先を維持する

注意点:

- **kSQL-Flow のローカルロックは cwd 単位**。切替でディレクトリが変わるとローカルロックの場所も変わる。分散ロック(JOBログ)が最終防御なので二重実行にはならないが、切替直後は旧ディレクトリの実行が終わるまで待つ運用にする
- **旧版のディレクトリは実行中の Run がある間は消さない**。NEW の bundle は添付に固定されるが、実行中のプロセスは旧ディレクトリのファイルを参照している。保持世代数を決めて古いものだけ消す
- cron の起動スクリプトは `current` の参照先だけを見る

### 4.2 Run の版表示

- 実行内容の識別は **bundle の sha256**(既に Run に残る)。Git のコミット ID は **由来情報** として追加で残し、ボードに両方を表示する
- 「公開版を更新しても既存 Run の resume 内容が変わらない」は、bundle が NEW 時に添付として固定される現在の設計で既に保証されている。新機能の受入条件にはしない

### 4.3 ボードの対応案内

- 結果コードごとに「次の操作 / 担当区分(一次・二次・サーバー担当) / 必要な証拠」を表示する。正本は一次対応者向け手順書と復旧 runbook。プラグインの文面追加のみで、状態機械と権限は変えない

## 5. SQL ジョブのアプリ管理を採らない理由と再審議条件

- **正本の二重化**: Git を正本にするとアプリは配布キャッシュでしかなく、§4.1 の配置で同じ効果が出る。アプリを正本にすると差分レビュー・履歴・CI の静的検査を失い、承認ハッシュで作り直すことになる
- **権限境界**: SQL は業務アプリへ書き込む。SQL アプリを編集できる人は、書込トークンを持つサーバーで動く内容を変えられる。allowlist の `app_start` を「人が名指しした network だけ」に限定した境界を、SQL アプリの ACL・承認者分離・ハッシュ照合で作り直す必要がある
- **既に成り立っているもの**: 既存 Run の SQL 固定は bundle で保証済み

再審議条件: **「Git を扱えない担当者が SQL の変更・承認を担う」という要件が確定したとき。** その場合は最初から、SQL アプリのトークンをサーバー側で読取専用にする、承認者を編集者と別ユーザーにする、承認レコードにハッシュを持たせる、NEW 時にハッシュ不一致なら拒否する、までを含めて仕様化する。
