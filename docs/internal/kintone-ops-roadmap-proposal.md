## 0.5 運用実体と、そこから導かれる前提

**本節が本書全体の優先順位を決めている。** ここが違っていれば、以降の結論はすべて変わる。

| 前提 | 内容 |
| --- | --- |
| P-1 | kSQL-FlowNet は完成直後であり、**本番運用の実績がまだない** |
| P-2 | 想定運用者は**中小企業の小規模な情シス担当**である |
| P-3 | 導入・運用に**ITベンダーが関与する可能性**がある |

### P-1 から導かれること

**実測データはまだ存在しない。** 本書の初版は「案A を作って1〜2か月測り、その結果で案C の要否を決める」という測定ドリブンの順序を提案していたが、**測る対象がまだ動いていない**。この論法は本番導入後にしか使えない。順序の根拠を組み直す必要がある(§4)。

**同時に、凍結仕様を直すコストが今だけほぼゼロである。** 本番データが1件もない = 移行対象が存在しない。§5・§6 で挙げる2件の修正は、**本番が1社でも載った瞬間に移行規則を伴う破壊的変更に変わる**。これは順序の判断を一変させる(§4.1 の `[0]`)。

**Phase 2 は現時点で投機的である。** 並列化が必要かどうかは、実行時間が締切を圧迫して初めて分かる。ユーザーがゼロの段階では誰もそれを要求していない。「実行時間が締切を圧迫しているか」という問いは、**現時点では答えられない**のが正しい答えである。

### P-2 から導かれること

**案A は「改善」ではなく「導入要件」である。** 小規模情シス担当に対して「`status --json` を実行して JSON を読み、`blocked_by` から復旧対象を判断せよ」は要求できない。**確認手段が kintone 画面にないと、そもそも運用を引き渡せない。** 初版では案A を「MTTA を縮める改善」と位置づけたが、この運用像では引き渡しの前提条件に格上げされる。

**「押さなくて済む」が「押せる」より価値が高い。** 一人運用では、夜間の失敗が自動で再試行されて朝には成功している状態が最も価値が高い。人がボタンを押す案B より、Phase 2 の**ノード単位リトライポリシー**のほうが先に効く可能性がある(§4.2-b)。

**案C(承認付き復旧)は、この体制では成立しない。** 申請者と承認者を別人にする二人制御は、担当が一人なら形骸化する。**P-3 が成立する場合に限り**、情シス担当=申請、ベンダー=承認という形で意味を持つ(§8)。

**押せるボタンの危険度が上がる。** 仕組みの理解が浅い担当者が押す前提になるため、UI側のゲートと CLI 側の fail-closed の両方が、初版で想定したより重要になる。特に §5 の `--rerun-from` の問題は、「ボタンを押したら必ずエラーになる」という形で担当者の信頼を最初に損なう。

### P-3 から導かれること

**責任分界点を、実装より先に決める必要がある。** 「情シス担当が押してよい操作」と「ベンダーが行う操作」の境界が、そのまま案B の受理範囲になる。ここが未定のまま作ると、要求アプリの権限設計をやり直すことになる。

**kintone を可観測性のインターフェースにすると、ベンダーがVPSへ入らずに一次診断できる。** これは副次的な効果だが小さくない。kintone は外部から閲覧でき、SSH や VPN を開ける必要がない。案A の価値は、社内向けだけでなく**ベンダーとの接点としても**評価すべきである。ただしゲストスペースまたはアクセス権の設計が別途要る。

## 2. 前提として確認した事実

以下はコードと定義ファイルから読み取った事実である。**推測を含まない主張だけを列挙した。**

| ID | 事実 | 確認箇所 |

| F-4 | Run 集約状態は、終端でも全 `SUCCESS` でもなく `started_at` があれば `RUNNING` を返す。一方 Invocation は `CANCELLED` / `NODES_DEFERRED` で終端する | `src/domain/run-aggregate.ts`、`src/orchestration/sequential-scheduler.ts` の `invocationOutcome` |

| F-6 | `OPERATION_AUDIT` は `event_type` を dropdown ではなく `result_code`(テキスト)へ、全ペイロードを `reason` へ書く。**新しい操作種別の追加にアプリのスキーマ変更は不要** | `src/persistence/kintone/repository.ts` の `appendOperationAudit` |
| F-7 | `RunInvocation.requested_by` は自由文字列である | `src/domain/persistence-model.ts` の `RunInvocation` |
| F-8 | 実装計画のマイルストーンは M0〜M7、すなわち Phase 1 のみ。Phase 2 は引き継ぎバックログに `P2-01` が1行あるだけで、計画は存在しない | `docs/implementation-plan.md` |

### F-1 から直ちに導かれる制約

**実行管理アプリのレコードを人が編集すると `$revision` が進み、orchestrator の書込みが `REVISION_CONFLICT` で失敗する。** プロセス管理のステータス操作もレコード更新なので同じである。実行中の Run に対してこれを行えば、当該ノードを `UNKNOWN` へ落としうる。

P-2 の運用像では、この事故の確率が上がる。担当者が「レコードを直せば直るのでは」と考えて実行管理アプリを開く場面は現実に起きる。**アクセス権で閲覧のみに固定し、画面上にも編集不可の理由を明示すること**を推奨する。

したがって本書のすべての案は、**実行管理アプリを機械専用に保つ**ことを共通の前提とする。人が書く場所は必ず別アプリとする。これは運用ルールではなく設計制約である。

## 3. 提案する構成(要約)

エラー確認とリラン指示のしくみを、独立に導入できる3つの面に分ける。

| 面 | 内容 | FlowNet改修 | P-2 での位置づけ |
| --- | --- | --- | --- |
| **案A** 確認ボード | kintoneプラグインで失敗ノード・`blocked_by`・最新Attemptを可視化。書込みなし | なし | **導入要件** |
| **案B** 要求アプリ+ポーラー | リラン要求専用アプリ + cron一発ポーラーが `run-network` を起動 | なし(§4.3) | 一次対応の自立化 |
| **案C** 承認付き復旧 | `UNKNOWN` / 非冪等 `FAILED` を承認フローと機械停止確認で扱う | あり | **P-3 が成立する場合のみ** |

不変条件は4つ。どの面でも破らない。

1. 実行管理アプリには人が書き込まない(F-1)
2. 指示はフラグではなく状態機械。`REQUESTED → ACCEPTED(起動前) → DONE / REJECTED`、落ちたら再発火しない
3. 要求者は kintone のシステムフィールド(更新者)を使う。フォームのテキスト欄を信用しない
4. 無人経路(ポーラー・ボタン起点)から回収系を呼ぶ場合は機械確認(`local_pid` / `cloud_run_job_execution`)に限定する。人がCLIで行う`manual`停止確認は凍結仕様どおり有効である(2026-08-31討論で改訂。旧文言「停止確認は機械が行う…」は凍結仕様D-29のmanual baselineと食い違うため置換)

## 4. 論点1(Dq-1): 着手順序

### 4.1 提案(改訂版)

```text
[0] 凍結仕様の修正2件                        ← 今すぐ。本番ゼロの今だけコストがゼロ
     ・--rerun-from の非冪等判定(Dq-2)
     ・Run.status セマンティクス(Dq-3)
       │
[1] 案A(確認ボード)                          ← 導入要件。測定手段ではなく引き渡し条件
       │
[2] Phase 2-a のうち ノード単位リトライポリシー ← 「押さなくて済む」が一人運用の最大価値
       │
[3] 初回本番導入(1業務・1ネットワーク)        ← ここが最大のマイルストーン
     ・ベンダーとの責任分界点を確定(Dq-4)
       │
[4] 実測                                     ← ここで初めてデータが出る
       │
[5] 案B / cancel伝播                          ← 実測を見て範囲を決める
       │
[6] 並列実行・trigger_rule拡張・リソースプール ← 需要が出てから。現状は投機的
       │
[7] 案C の要否判定                            ← P-3 が成立する場合のみ
```

**初版からの主な変更**

| 項目 | 初版 | 改訂版 | 理由 |
| --- | --- | --- | --- |
| 仕様修正2件 | Phase 2 の審議に合わせる | **最優先で単独実施** | P-1。本番が載る前だけ移行コストがゼロ |
| 案A の位置づけ | 測定のために先に作る | **導入要件として先に作る** | P-2。CLIでの状況把握を要求できない |
| 初回本番導入 | 記載なし | **ロードマップの中心に明示** | P-1。作る順番より載せることが先 |
| Phase 2-a | retry + cancel をセット | **retry を先行、cancel は後ろ** | P-2。自動回復 > 手動停止 |
| 並列化 | Phase 2-b として案B の後 | **需要が出るまで着手しない** | P-1。現状は完全に投機的 |
| 案C | 実測次第 | **P-3 が成立する場合のみ** | P-2。一人では二人制御が成立しない |

### 4.2 根拠

**(a) `[0]` を最優先にする理由。** 本番データがゼロである今、凍結仕様の変更は移行規則を必要としない。本番が1社でも載れば、`--rerun-from` の判定変更も Run.status の意味変更も、既存レコードの解釈をどうするかという問題を伴う。**この窓は二度と開かない。** 加えて §5 の問題は、P-2 の担当者が最初に押すボタンが必ずエラーになるという形で顕在化するため、導入初期の信頼を直接損なう。

**(b) `[2]` にリトライポリシーを置く理由。** P-2 では担当が一人であり、夜間・休日の即応は期待できない。「人が気づいてボタンを押す」(案B)より「気づく前に自動で直っている」(リトライポリシー)のほうが、この運用像では価値が高い。案B は、リトライで吸収しきれなかった残りを扱う位置づけになる。

したがって**リトライポリシーを先に入れると、案B の必要範囲が実測で確定してから作れる**。順序として無駄がない。

**(c) `[3]` を明示する理由。** これまでの議論はすべて「何を作る順番」だったが、P-1 の下では**最大のリスクは未実装機能ではなく、初回導入が成功するかどうか**である。移行runbookと復旧runbookは既にある(`runbook-phase1-migration.md`、`runbook-phase1-recovery.md`)ので、素材は揃っている。1業務・1ネットワークに限定して載せ、そこで出た問題を次の投資判断の入力にする。

**(d) `[6]` を後退させる理由。** 並列化の受入条件は「逐次実行と同じ最終状態・監査結果になること」であり、検証コストが高い。それを、誰も速度を要求していない段階で払う理由がない。**本番が1本動いて実行時間が問題になってから着手しても遅くない。** 逆に、その時点なら案A が観測装置として使えるため、検証コストは下がる。

**(e) 案A は kintoneプラグイン、Phase 2 はFlowNetコアであり、作業の性質が異なる。** 並走は可能であり、案A は Phase 1 凍結に触れないため FDR審議とも競合しない。

### 4.3 案B が FlowNet 無改修で通る理由

F-7 より、`--requested-by "kintone:<request_id>:<更新者コード>"` を渡せば、既存フィールドで要求と Invocation の相関が取れる。**Phase 1 のスキーマにも CLI 引数にも触れない。**

ただしこれは stopgap であり、負債として記録すべきである。

- 構造化されていないため検索・集計が弱い(前方一致依存)
- 後に `request_ref` を正式フィールド化する際、文字列形式の既存データに移行規則が要る
- **フォーマットを最初に固定して文書化する**。後から変えると過去データが2形式になる

なお P-1 の下では、`request_ref` の正式フィールド化も**本番導入前なら移行不要**である。案B の着手が `[5]` と後ろになるため、そのときには本番データが存在する。**stopgap を選ぶか、`[0]` のタイミングでフィールドを足しておくかは、担当CCの判断を仰ぎたい**(§7 Q-C)。

### 4.4 想定される反論

**R-1「本番がないなら、まず本番に載せるべきで、案A も後回しでよいのでは」**
→ 部分的に同意する。ただし P-2 の担当者に引き渡す条件として確認手段が要る。**開発者自身が張り付いて運用する初期期間を設けるなら**、案A を導入後に回す判断はありうる。その場合でも `[0]` の優先度は変わらない。**この反論は真剣に検討する価値がある**(§7 Q-A)。

**R-2「リトライポリシーは Phase 2 の一部であり、Phase 2 の仕様策定が先に要る。分割できないのでは」**
→ 分割可能性は担当CCのほうが判断材料を持つ。分割できないなら `[2]` は `[3]` の後へ回し、初回導入は Phase 1 のまま行う。**この点は §7 Q-B で確認したい。**

**R-3「ベンダーが運用するなら CLI で十分であり、案A/B は不要では」**
→ P-3 は「可能性あり」であって確定ではない。またベンダーが入る場合でも、一次確認を情シス担当が行い、二次対応をベンダーが行う二層構造が自然であり、一次側には画面が要る。加えて、kintone経由の確認はベンダーがVPSへ入らずに済むという利点がある(§0.5)。

**R-4「案A の効果が測れないまま案B に進むのでは」**
→ 改訂版では案B は `[5]`、すなわち初回本番導入と実測の**後**に置いた。この懸念は解消している。

### 4.5 判断が変わる条件

1. **初期は開発者自身が運用する期間を設ける** → 案A を `[3]` の後へ回せる。`[0]` は変わらない
2. **リトライポリシーが Phase 2 の他項目から分離できない** → `[2]` を `[3]` の後へ
3. **P-3 が確定し、ベンダーが運用主体になる** → 案B の優先度が下がり、案C の前提が成立する

## 5. 論点2(Dq-2): `--rerun-from` の非冪等判定 【クローズ済み】

> **2026-08-31クローズ**: 本節の提案はR2-1再審議として実施済み(FDR §13、実機E2E m7-05合格、mainマージda9056b)。以下は記録として残す。

### 5.1 現状と問題

F-3 のとおり、`--rerun-from` は対象集合に `idempotent = false` のノードが1つでもあれば拒否する。判定材料は定義上の `idempotent` だけで、**そのノードが実行済みかを見ていない**。

仕様書 §4.1 の `monthly_close` は `extract_sales → aggregate_customer → send_invoice(idempotent: false)` である。したがって §9 に記載されている CLI 例

```bash
ksql-flownet run-network monthly_close --resume-run ... --rerun-from aggregate_customer
```

は `send_invoice` を子孫に含み、**常に拒否される**。仕様書内で例と規則が矛盾している。

非冪等な終端ノード(通知・請求・外部連携)を持つDAGは実務上ほぼすべてこの形になるため、`--rerun-from` が使える場面がほとんど残らない。

**P-2 の下では影響が大きい。** 案B のボタンのうち「指定ノードからリラン」は、この状態では押すたびに必ずエラーを返す。仕組みに詳しくない担当者にとって、これは「このツールは動かない」という最初の印象になる。

### 5.2 §7.1 との非対称

通常 resume(§7.1-6)は `BLOCKED` を冪等性に関係なく `WAITING` へ戻す。したがって**未実行の `send_invoice` は `--resume` なら実行される**のに、`--rerun-from` では同じノードが対象集合全体を止める。同一仕様内で扱いが割れている。

### 5.3 提案する修正

二重実行リスクがあるのは「すでに attempt が存在する非冪等ノード」だけである。判定を次に絞る。

> 対象集合のうち、`idempotent = false` **かつ** `latest_attempt_no > 0`(または status が終端)のノードがある場合に拒否する

未実行の非冪等ノードの初回実行を拒む理由はない。

### 5.4 手続き(改訂)

凍結仕様の変更にあたるため FDR の再審議が要る。修正自体は判定条件の絞り込みなので小さいと見込まれるが、**受入基準12の試験内容の更新を伴う**。

初版では「Phase 2 の仕様策定と同じ審議に載せる」としたが、**改訂版では単独で、本番導入前に実施することを提案する**(P-1)。Phase 2 の着手時期がまだ決まっていない以上、そこに紐づけると本番導入に間に合わない可能性がある。

### 5.5 想定される反論

**「意図的に厳しくしてある。非冪等ノードを含むサブツリーの再実行は専用の運用フローへ分離するのが §7.2 の趣旨である」**
→ 趣旨には同意する。ただし現状の判定は「専用フローへ分離」ではなく「サブツリーに非冪等な葉があると再実行機能そのものが使えない」になっている。§7.1 が未実行の非冪等ノードを実行する以上、`--rerun-from` だけが実行済みか否かを区別しないのは整合しない。**この反論が正しい場合でも、§9 の CLI 例か §4.1 の例DAGのどちらかは直す必要がある**(現状の文書は矛盾している)。

## 6. 論点3(Dq-3): Network Run 集約状態

### 6.1 現状

F-4 のとおり、終端でも全 `SUCCESS` でもない Run は `started_at` があれば `RUNNING` を返す。一方 Invocation は `CANCELLED` / `NODES_DEFERRED` で正しく終端する。したがって**プロセスが1つも生きていない Run が `RUNNING` を名乗る状態**が正常系として存在する(lease drain 後、`LOCK_CONFLICT` で `WAITING` に戻した後など)。

P-2 の下では、これは監視の誤検知より深刻である。**担当者が画面で「実行中」と読んで待ち続ける**という形で現れる。夜間バッチが止まっているのに「まだ動いている」と表示され、翌朝まで気づかない。

### 6.2 案A のブロッカーではない

当初、案A の前提として先に修正が必要と考えたが、**これは誤りである。撤回する。**

F-5 のとおり `NETWORK_LOCK` レコードは実行管理アプリにあり、`owner_invocation_id` / `lease_expires_at` / `heartbeat_at` を保持している。したがって

> 「未完了」かつ「lock owner不在、または lease失効」= **中断中**

をプラグイン側で導出できる。**仕様にも実装にも触れずに「対応が必要な Run」の一覧が作れる。**

### 6.3 提案(改訂)

初版では「Phase 2-b と同時に見直す」としたが、**改訂版では `[0]` に置く**。理由は P-1(移行コストが今だけゼロ)と、6.1 の運用上の影響である。

修正の方向は2案ある。討論の対象としたい。

- 案i: `status` に中断を表す値を追加する(集約状態表の変更。本番導入後なら移行影響あり、**今なら影響なし**)
- 案ii: `status` は変えず、`status_reason` または派生フィールドで区別する(影響小、監視側の実装が要る)

**P-1 の窓が開いている今に限り、案i のコストが案ii と変わらない。** 本来望ましいほうを選べる稀な状況である。

## 8. 案C の扱い(改訂)

初版では「実測データが既存の監査履歴アプリに揃っている」と書いたが、**P-1 によりデータはまだ存在しない**。この記述は本番導入後にのみ有効である。訂正する。

案C の要否判定は `[7]` に置き、判定材料は初回本番導入後に貯まる次のデータとする。

| 知りたいこと | データ源 |
| --- | --- |
| 状態別の停止頻度 | Node Attempt の `status` / `result_code` 分布 |
| リトライポリシーで自動回復した割合 | `RUN_INVOCATION` の `mode = RESUME` かつ `requested_by = cron` の成否 |
| 人が介入した回数 | `requested_by` が cron 以外の Invocation 件数 |
| 案C が必要な事象の実数 | `ATTEMPT_RESOLUTION` レコードの件数と `resolved_outcome` |
| 案B で救えなかった件数 | `UNKNOWN` / 非冪等 `FAILED` で終わった Node State |

**着手前に閾値を決めておくことを提案する。** 「`ATTEMPT_RESOLUTION` が月N件を超えたら案C を設計する」の N を先に合意しておかないと、判断が先送りされ続ける。

### 案C の成立条件が変わった

P-2 の下では、案C の中核である**二人制御(申請者≠承認者)が組織的に成立しない**。担当が一人なら、申請も承認も同一人物が行うことになり、承認フローは形式だけ残って安全性に寄与しない。

したがって案C の前提を次のように書き換える。

> **案C は、P-3(ベンダー関与)が確定し、かつベンダーが承認者として機能する契約がある場合にのみ検討する。**

この場合、承認者が社外にいることから追加の論点が生じる。

- 承認のレスポンス時間が読めない(夜間の復旧が翌営業日になりうる)
- ベンダー側のアクセス権をどう与えるか(ゲストスペース、アカウント管理)
- 監査要件が上がる(社外の主体による本番データ操作)

**逆に P-3 が成立しないなら、案C は設計しない**という判断を先に置いてよい。頻度を測るまでもなく、体制として成立しないためである。

### 案C を止める理由の明確化

案C を今やらない理由は「スキーマ変更が必要だから」**ではない**。F-6 のとおり、監査側は新しい操作種別を足してもアプリのスキーマ変更を要さない。

本当の理由は次の3つである。

1. **体制として成立しない**(P-2。P-3 が確定するまでは前提が欠けている)
2. 必要性がまだ実測されていない(P-1)
3. 停止確認 adapter(FN-15)をポーラー経路から正しく呼ぶ実装が要り、ここを手抜きすると安全性が形骸化する

**この区別は重要である。** 「スキーマが障壁」と誤認していると、将来スキーマ変更のついでに案C を入れてしまう。実際には、必要性が立証された後であっても、停止確認 adapter を経由しない実装なら入れてはならない。
