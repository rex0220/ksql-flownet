# 運用改善案 別紙: AI 運用アシスタントの将来構想

- 文書状態: **将来構想**(討論の結論。決定ではない。実装の起票は本紙 [運用改善案](./ops-improvement-proposal-20260907.md) の第 1〜第 3 段階の後)
- 作成日: 2026-09-07
- 経緯: ChatGPT の「AI を利用したバッチジョブ管理の 5 段階」構想を、担当 Claude Code が FlowNet の状態機械・権限境界・既存の操作要求経路と突き合わせて 2 巡で討論した結論
- 方針: **既存の CLI と状態機械を実行の責任者に据え、その上に読取専用の AI 運用アシスタントを追加する。** AI の説明を新しい正本にしない。自動対応は AI の自信ではなく明示的な条件で許可する。最初の到達目標は「自動復旧」ではなく **「副担当が AI の説明と証跡を使って、主担当と同じ手順で対応できること」**

## 1. 5 段階の到達点と受入

| 順 | 到達点 | AI が担当 | 人が担当 | 主な受入 |
| --- | --- | --- | --- | --- |
| 1 | 読取専用の説明・診断 | 実行状況、失敗箇所、影響範囲の説明。証跡と runbook の照合、原因候補と追加確認の提示 | 内容確認、原因と対処の判断 | 根拠のない因果を作らない。古い情報・取得失敗を明示する |
| 2 | 復旧準備書の作成 | 再開対象と選定理由、成功済みと再実行される処理、入力固定・ロック・再開許可の確認結果、業務影響、実行予定の操作と承認が必要な理由 | 承認 | 対象・影響・必要証拠を runbook と整合させる |
| 3 | 承認付き操作要求 | 操作要求アプリへの起票(§4) | 承認、例外判断 | 内容変更、状態変更、再送、自己承認を拒否する |
| 4 | 変更支援 | SQL・network の変更案、テスト、配置計画 | 差分レビュー、承認 | レビュー・検証・版別配置を通した変更だけを公開する |
| 5 | 業務改善の候補提示 | 集計の共通化、重複転記、日次・月次の定義差、回帰テストの選定、件数・合計の異常の説明 | 業務設計の変更判断 | 許可された情報と期待条件の範囲で提案する |

段階 1・2 は本紙の第 1 段階(doctor・diagnose・heartbeat・期待 Run 照合)の成果物を材料にする。段階 3 は操作要求の状態機械と権限の拡張であり、P2-16 と同じく個別仕様・外部レビュー・凍結・実機 E2E を要する。段階 4 は本紙の第 2 段階(版別配置)が前提。段階 5 は §6 の情報境界を先に決める。

## 2. AI に渡す語彙: 事実・宣言・仮説

説明の材料は既に決定的に作れる。結果コード、activity、hold、`recovery_identifiers`、Attempt と JOBログの突合は `status --json` にあり、結果コードごとの次の操作は一次対応者向け手順書にある。AI が足す価値は自然言語化と複数 Run をまたいだ要約で、そのために足りない語彙が 2 つある。

- **業務のまとまり**: 「締め処理 = 売上集計 + 請求集計 + 管理資料作成」という束は定義されていない。本紙 §3.4 の監視設定ファイルに「業務名 → network の一覧と順序」を **宣言的なメタデータ** として置く。実行の意味論は持たせず、説明と監視にだけ使う
- **network 間の順序**: 統合仕様書 §9 のとおり network 間依存は未対応で、ASSERT ゲートによる fail-closed の連鎖で代替している。**宣言された順序と、実装が強制する依存を区別する。** 順序の宣言だけでは停止原因の証明にならない

説明では事実・運用上の宣言・仮説を分ける。

> 請求集計は FAILED、管理資料作成は Run 未作成です。運用設定では請求集計を先に実行する順序です。管理資料作成が未実行である原因は、取得した証跡では確定できません。

network 間の因果を事実として言える経路は ASSERT ゲートだけである。後続 network の先頭ノードが前提の未完了を ASSERT で検査して止まった場合、その Attempt の失敗メッセージが証跡になる。ゲートの ASSERT メッセージを機械可読な形(例: `UPSTREAM_INCOMPLETE:<network_id>`)に揃える運用規約を置けば、AI は「ゲートで停止。メッセージは請求集計の未完了を示す」と事実として言える。メッセージがなければ「原因は確定できない」に落とす。

## 3. 根拠の契約と検証

- すべての主張に根拠を付ける。根拠は識別子(run_id、attempt_id、request_id、event_id)だけでなく **項目・値・取得時刻** を含む。根拠を付けられない主張は「根拠なし」と明示する
- 根拠の検証は AI に任せず **決定的なチェッカー** で行う。AI の出力を「主張」と「根拠」の JSON にし、チェッカーが根拠の項目を再取得して値を比較し、支持 / 不一致 / 取得不能 を付ける
- 不一致か取得不能を含む主張は、復旧準備書に載せられても **許可条件には使えない**。根拠のない仮説を復旧操作の許可条件に使わない
- 古い情報(heartbeat の途絶、評価失敗)と取得失敗は、本紙 §3.4 の状態契約どおり明示する

## 4. 承認付き操作要求(段階 3)の設計論点

AI に復旧コマンドを持たせるのではなく、**AI を「操作要求アプリに起票する 1 人の要求者」にする。** allowlist の `app_start`、claim、revision 競合、claim 前の取消、`requested_by` 付きの監査がそのまま効き、ボードで誰でも見え、取り消せる。直接 CLI を渡すより権限を限定しやすい。ただし以下は既存経路の拡張であり、仕様として固める。

### 4.1 承認対象の固定

- 要求種別、対象(run_id か network_id + 業務キー)、対象ノード、前提条件のダイジェスト、提案 ID を正規化した文字列のハッシュを `approval_hash` にし、人が承認するときにその値を書く
- ポーラーは claim 時にハッシュを再計算し、一致しなければ `REJECTED / APPROVAL_MISMATCH`。承認後の内容変更は再承認
- 自己承認は運用規約ではなく **kintone のフィールドアクセス権** で止める。承認フィールドを AI 用ユーザーに編集不可にすれば、AI のトークンでは書けない

### 4.2 前提条件の範囲と保証時点

- Run の `revision` だけでは hold や Node State の変更を拾えず、新規 START には Run がない。前提条件は **FlowNet が計算する状態ダイジェスト** にする。`status --json` が、Run の revision・hold・ロック・Node State の revision・その Run に対する未終端要求を束ねた `state_digest` を返す。新規 START では「その業務キーに未終端 Run がないこと」と allowlist の版を束ねる
- 保証時点は **Network ロック取得直後**。claim 時にポーラーが照合し、CLI がロックを取った直後にもう一度計算して不一致なら `REJECTED / PRECONDITION_FAILED`。ロック取得後は他の run-network が状態を変えられないので、「ロック取得時点の状態が提案時点と同じ」までを保証する。要求側の変更(取消)は既存の claim 競合の裁定が効く
- ensure-run が実行時に行う再検査(`RUN_ALREADY_EXISTS`・`NOOP_ALREADY_SUCCESS`・`RETRY_BRAKE`・hold)はそのまま残す

### 4.3 本人性と重複

- API トークンで作ったレコードの作成者は Administrator になる(既知の制約)。AI の本人性はトークンではなく、レコードの `requested_by` と、AI 専用トークン 1 本を 1 主体に対応させる台帳で担保する
- 応答喪失後の再送で要求が増殖しないよう、`proposal_id` を重複禁止フィールドにし、kintone の一意制約で弾く(NEW の線形化点と同じ仕組み)

### 4.4 承認待ちの状態

- `REQUESTED` の前に `PROPOSED` を置く。取消は PROPOSED にも効かせる。stale 判定は claim 後の話なので影響しない
- PROPOSED には有効期限を置き、期限切れは `REJECTED / PROPOSAL_EXPIRED`
- 単一フィールド PUT の例外は取消だけに残し、承認は状態遷移として扱う。**取消と同じ単一フィールド PUT という形だけでは同等の安全性は得られない**

### 4.5 許可範囲の目安

| 操作 | 扱い |
| --- | --- |
| 診断情報の収集、状態の再確認 | 自動化しやすい(読取専用) |
| 通知・引継ぎ票の下書き | 自動化しやすい |
| 検証環境でのテスト | 対象と権限を限定して自動化 |
| 本番の再開 | 冪等性だけでなく、入力・状態・業務条件を検査して限定許可(§4.1〜§4.4 の契約が前提) |
| UNKNOWN の裁定 | 証拠収集は AI、結果確定は人 |
| 強制解放、補正 Run、SQL 公開 | 人の判断を維持(停止確認という物理的な行為を含む) |

一時的な通信エラーのリトライなど、条件が完全に定義できる処理は通常のコードで実装する。AI の役割は、複数の証跡を読んだ説明、例外の整理、変更案の作成にある。

## 5. 変更支援(段階 4)

- 開発側では既に回っている型(Codex 実装、`validate` / `plan`、kSQL-Flow の dry-run、検証環境の smoke)を運用側へ持ち込む
- AI が作った変更は、本紙 §4.1 の版別配置(dirty 拒否、`validate` / `plan`、配置ロック)を通ってからしか本番に届かない。配置手順は SQL の業務上の安全性まで保証しないため、差分レビューと承認は人が行う

## 6. 業務改善の候補提示(段階 5)の前提

- FlowNet が持つのは実行の証跡(読取・書込件数、時刻、結果コード)であって業務データではない
- 件数や合計の異常検出は、期待範囲を設定に書く **決定的な監視** として先に作る。AI は「通常と異なる」の説明役にとどめる。件数の異常を検出してもデータを補正せず、「正常に終了したが業務確認が必要」という情報として扱う
- SQL の重複や不要な転記の発見は kintone-sql-tools 側の解析。業務データを AI に読ませる境界(個人情報、書込トークン)を先に決めない限り着手しない

## 7. 測定

本紙 §6 の測定に加えて、AI 併用の復旧訓練では次を測る。

- 誤った操作提案の件数
- 根拠不一致の件数(§3 のチェッカーの結果)
- 必要なエスカレーションの見落とし
- 承認拒否率(0 なら承認の形骸化、高すぎれば提案の質の低さを疑う)

速くなることと、安全に副担当へ引き継げることを両方確認する。訓練は「副担当 + runbook」と「副担当 + runbook + AI」の 2 条件で行う。
