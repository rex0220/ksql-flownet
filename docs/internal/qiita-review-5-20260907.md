対象: docs/internal/qiita-draft-5.md(commit 5f49618)。正本 docs/scheduling-patterns.md にも同じ問題があったため、記事と正本の両方へ反映した。

| # | 指摘 | 裁定 | 反映・根拠 |
| --- | --- | --- | --- |
| 必須 1 | 直列連結スクリプトが kSQL-FlowNet の環境ファイルを読んでいない(cron から直接呼ぶと失敗) | 採用 | スクリプト冒頭で `/root/.ksql-flownet.env` を source。cron 行(`flock -n` 付き)を併記。正本のスクリプトも同じ修正 |

| 必須 3 | `COUNT(*) > 0` では上流の完了を証明できない(部分書込み・0 件正常・残存データ)。「最も確実」は言い過ぎ | 採用 | 「Run の記録より実態に近い」へ弱め、成立条件(正常完了なら必ず 1 件以上・部分書込みが残らない)を明記。満たせない業務向けに完了マーカー(`状態 = 'COMPLETE'` が 1 件)の例を追加。正本も同じ修正 |
| 補足 1 | `MAILTO` は MTA / メールリレーがないと届かない | 採用 | 条件付きの表現へ(記事・正本) |
| 補足 2 | 「cron は再起動耐性が高い」は停止中の発火を補完するように読める | 採用 | 「サービスとして管理でき監視対象を増やさない。停止中の発火は補完しないので、未実行期間はボードで検知し SCHEDULED_FOR で流す」へ(記事・正本) |
| 2b | 対象月の SUCCESS 条件は補正 Run も通す。意図の明示または business_key 照合 | 採用(意図を明示) | 「通常 Run・補正 Run のいずれでも対象月の正常な成果があればよい。定期キーだけなら business_key も照合」を追記(記事・正本) |
