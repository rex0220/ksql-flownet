## 1. 出発点

「kSQL は CSV / JSON を import できるのに export できない」という非対称から始まり、他システムへのデータ提供、FlowNet への CSV 出力、シェルノードの可否まで一連で検討した。以下はその結論をまとめたもの。

## 3. 設計の骨格 — アダプタ + マーカー

外界の都合(いつ届くか、どのプロトコルか、どの文字コードか)を **FlowNet の外のアダプタが吸収**し、FlowNet は kintone のデータとマーカーだけを見る。入口と出口が対称になる。

```
[受信cron: 取込アダプタ]                              [配信アダプタ]
  ファイル発見                                          マーカー READY を検知
  → VALIDATE ONLY で全行検証                            → export して相手へ送信
  → IMPORT ... ON DUPLICATE(冪等)                       → 配信結果をマーカーへ書戻し
  → [取込マーカー] business_key/sha256/rows                     ▲
        ↓ 外部Triggerとして run-network を起動                  │
  ┌──────────────── kSQL-FlowNet ────────────────────────────┐ │
  │ 先頭ノード: ASSERT でマーカー確認(無ければ fail-closed)  │ │
  │ … SQLノード群(加工)…                                    │ │
  │ 最終ノード: publish(UPSERT)→ [公開マーカー] ────────────┼─┘
  └──────────────────────────────────────────────────────────┘
```

| | 取込アダプタ(入口) | 配信アダプタ(出口) |
| --- | --- | --- |
| トリガ | ファイル到着(ポーリング) | マーカーが `READY` |
| 実行するもの | `IMPORT`(kSQL CLI) | export(cli-kintone / kSQL CLI) |
| 冪等の担保 | `ON DUPLICATE` + ファイル sha256 の重複禁止 INSERT | 版の固定 + 全量上書き |
| kintone に残すもの | 取込マーカー | 公開マーカー + 配信ステータス |
| FlowNet との接点 | 先頭ノードの `ASSERT`、および外部 Trigger としての起動 | 最終ノードの publish |

**両アダプタとも P2-01 の `poll-requests` ポーラーと同型**(one-shot、cron 起動、状態は kintone、fail-closed)。既に実機で通した型の再利用であり、新しい実行基盤ではない。

### 3-1. データ提供で push を採らない理由

外部送信はすべて非冪等な副作用で、Phase 1 §4.2 が「外部への通知は完全に決定的でも非冪等」と名指しする類型。resume(§7.1)と chunk リトライで再送され、結果が確定できなければ `UNKNOWN` が業務に残り、相手の認証情報を FlowNet が抱えることになる。**提供とは「相手が読める場所に置くこと」**で、置く操作(`UPSERT`)は冪等。

ただし相手が pull できない場合(パッケージ、SaaS、取引先のベンダー製システム)は現実に多い。その場合は**こちら側に配信アダプタを置く**。相手から見えるものは変わらず、非冪等な転送だけが FlowNet の外に出る。

### 3-2. 提供アプリを挟む理由(相手が読むかどうかとは独立)

- **断面が固定される** — 業務アプリ直読みだと、読んでいる最中の更新で中途半端な断面を配信しうる
- **再配信が冪等になる** — 版が固定されていれば「同じ版をもう一度送る」で済む。**転送という非冪等操作を、内容の不変性で実質冪等に落とす**
- **何を送ったかが残る** — 直読み+送信だと送った中身を再現できない

### 3-3. マーカーが与えるもの

kSQL にトランザクションはない(§22)。**それでも相手に一貫した読み取りを保証できるのは「全部書き終えてから最後にマーカーを立てる」順序だけ**で、その順序を機械的に保証するのが安定トポロジカル順と `trigger_rule: all_success` — つまり **DAG の本来用途にそのまま乗る**。

失敗時は自動的に安全側に倒れる: ノードが `FAILED` / `UNKNOWN` / `CANCELLED` ならマーカーが立たず、相手は**前版を読み続ける**。不完全なデータを見せる経路が構造的に存在しない。

publish ノードは `UPSERT` なので**全ノード冪等が維持され**、P2-11 の三重ゲート③を満たしたまま、補正版の再公開をボードから START できる。

## 4. 各論の結論

| 案 | 結論 | 主な理由 |
| --- | --- | --- |
| kSQL に `EXPORT` 文を追加 | **不要** | 射影・整形は SELECT が担っており、言語で表現すべき意味論が無い。SQL がパスを持つと IMPORT の off-by-default と逆行 |
| **FlowNet 本体**に CSV 出力 | **却下** | F-4 を壊す。Execution Result が데ータ量に比例し、監査アプリに業務データが載る |
| **kSQL-Flow / kSQL CLI** に出力オプション | **妥当**(ただしコストは中〜大) | 実体は engine への追加(§5)。CLI 製品としての非対称解消には意味がある |
| 出力対象の指定 | **名前付きシンク**。`--export-csv <name>=<path>` で `#name` を出す。単文 SELECT のときのみ名前省略可、複文はエラー | 「最後の SELECT」は編集で壊れ、R1 の型(末尾は完了 UPDATE)や R11 の型(末尾は `SELECT * FROM #err`)と衝突する |
| FlowNet ノードでの IMPORT | **現状不可、追加も推奨しない** | F-3。入力を bundle に入れると F-5 により業務データが実行管理アプリの添付になる。入れないと resume の再現性が入力ファイルの寿命に依存 |
| **任意シェル**ノード | **反対** | Node ロックの外(F-7)、冪等が無検査、Contract 適合が案件ごとにばらつく、bundle が半分しか効かない。ADR §9 の棄却理由に戻る |
| **登録済みコマンド**ノード | **executor 拡張の最初の形として妥当**。ただし着手条件を先に決める | 定義に書けるのはコマンド名(allowlist キー)と引数だけ。`lock_key` / `idempotent` / 通す環境変数を allowlist エントリで運用者が宣言する |
| `cli-kintone` をコマンド登録 | **唯一の正当な登録動機がある** | 添付ファイル(FILE)は kSQL IMPORT が構造的に非対応で、Contract を拡張しても解決しない |
| `kSQL-cli` をコマンド登録 | **しない** | ノードは既に kSQL-Flow 経由で SQL を実行している。別コマンドとして登録すると **Contract を通る経路と通らない経路の2つ**ができ、監査・ロック・as-of 固定・bundle が片方だけ効く |
| まずアダプタ + `ASSERT` で運用 | **現時点の推奨** | 順序の表現力だけが動機なら、実測してから判断する(原則4) |

### 4-1. 一般則(判定基準)

> **既存 executor(kSQL-Flow)で到達できる機能は Execution Contract を拡張して吸収する。構造的に到達できない機能だけをコマンド登録する。**

`IMPORT` / `EXPORT` は前者(Contract v1.1 に `--import-csv` / `--export-csv` と capability を足せば届く)。添付ファイルは後者(kSQL の非対応が構造的)。この線引きが、executor 拡張を無制限に広げないための実務的なゲートになる。

### 4-2. 登録済みコマンド方式にした場合の要件

- 定義に書くのは**コマンド名と引数**のみ。実行パス・許可する環境変数・`lock_key`・`idempotent` は **VPS 上の allowlist ファイル**が持つ(P2-11 の `app_start` と同じ「運用リリース判断がファイルに残る」形)
- **冪等性を引数の形で強制する** — `cli-kintone record import` は `--update-key` 必須(= UPSERT)。`--update-key` なしは allowlist で禁止。export は読み取りなので当然冪等。**宣言ではなく構造で担保できるのが、任意シェルとの決定的な違い**
- **Contract 適合は汎用ラッパーが1度だけ担う** — exit code と件数を Execution Result へ変換。**JOB ログアプリへの耐久 `EXECUTION_STARTED` はラッパーの責務**(cli-kintone は書かないため。これは「実行したか不明」の裁定材料なので省略不可)
- `lock_key` は SQL ノードの `job_id` と同じ名前空間に置くか決める。同じアプリを触る SQL ノードとの競合を検出したいなら必要で、その場合は `__net__` のような予約語規約が要る

## 5. CSV 出力を「kSQL への追加」と見るべき理由

`--export-csv` という CLI オプションの見た目に反して、決めるべきことのほぼ全部が **engine の値表現**である。

- **数値** — 生値は文字列保持だが、算術を通った列は IEEE 754 の誤差がそのまま出る(`3300.0000000000005`)。§22 が「`UPDATE SET` で保存すると差が保存データへ残る」と警告している問題が、**CSV では社外のシステムへ流れて固定される**
- **空セル / NULL の表現、日時の書式とタイムゾーン、複数値のセル内表現、サブテーブルの `*` 形式、Shift_JIS で出力できない文字の扱い**
- **列名の小文字正規化**(F-9) — 素直に出すと CSV ヘッダが kintone のフィールドコードと一致せず、**自分で出した CSV を自分の `BY NAME` で読み戻せない**。出力時の明示的な例外規則が要る
- **量が理由なのに、その量域で engine が持たない**(F-8)。数万件級を毎月出すならストリーミング出力=メモリモデルの変更が本体で、CSV シリアライズはその上の薄い層
- 一度出した値表現は**対外契約**になり、バージョン間で変えられなくなる。ADR §8 の利点「既存利用者と軽量性を維持できる」と衝突

**層分けの結論**: engine がシリアライズ(IMPORT の逆写像と同じ場所)、面がシンクを供給する。IMPORT が「面がソースを供給し engine が変換する」形の鏡像にする。

| 面 | ソース供給(IMPORT) | シンク供給(EXPORT) |
| --- | --- | --- |
| CLI | `--import-csv <name>=<path>` | `--export-csv <name>=<path>`(`-` で stdout 可) |
| ksql-flow | 同上 | 同上(**stdout 不可** — Contract §6「`--result-json -` では stdout へ JSON 以外を出力しない」と衝突するため) |
| MCP | inline `importSources` | inline `exportSinks` |
| プラグイン | ファイル選択 | ダウンロード |

**共有すべきは「名前で結ぶ意味論」**。SQL は CLI で書いて試し、flow が本番で回すため、**同じ SQL ファイルが CLI でも flow でも同じものを出す**ことが不変条件になる。

なお FlowNet から見れば、flow に `--export-csv` があれば**パスを subprocess 引数で渡すだけ**で、データは FlowNet を通らない(F-4 を維持)。その場合 Execution Result へ `output_files: [{name, sha256, rows, bytes}]` を記録すれば、**レコードを1件も持たないまま「何を出したか」の同一性を監査できる**。

## 6. 検討中に行った自己訂正

| 訂正 | 内容 |
| --- | --- |
| ファイル出力は非冪等 → **誤り** | 通知は取り消せないがファイルは上書きできる。①同一パスへ全量上書き ②一時ファイル+rename ③as-of 固定、の3条件で**冪等**。§4.2 が挙げる非冪等の例のどちらでもない |
| CSV 出力は executor 拡張 → **誤り** | 新しいコードを走らせないので ADR §7 の8前提のうち sandbox・任意コード・補償は不要。帳票・SFTP・画像処理が executor 拡張 |
| kSQL-Flow への追加は「小」 → **誤り** | 追加先は engine(kSQL)であり、規模は中〜大(§5) |
| 提供アプリは「相手が読む場所」 → **不十分** | 価値は配信の再現性・冪等性・監査であり、相手が pull しなくても残る(§3-2) |
| IMPORT の値表現は新規設計 → **言い過ぎ** | IMPORT 実装時点で CSV↔kintone 型の対応は半分決まっており、export はその逆写像 |

## 7. 次に決めること

1. **提供する件数**。数千件までなら提供アプリだけで完結し、CSV 出力は不要
2. **相手はファイルを要求しているのか、量が理由か**。前者なら配信アダプタでの変換で足りる
3. **取込/配信アダプタで足りない業務が2件以上あるか**(executor 拡張の着手条件の形)
4. **取込失敗をどこに出すか** — ボードの「要対応(終端)」に出す(Run を作って先頭 `ASSERT` で FAILED)か、取込マーカーアプリの一覧で運用するか。**二重管理を避けるためどちらかに決める**
5. **doc gap の解消** — IMPORT に言語リファレンスの独立節を作る(F-2)。`ENCODING` 句の位置、句の順序、`CHECK WHEN` の完全形が現在どこにも書かれていない
