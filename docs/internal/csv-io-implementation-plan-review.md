## 1. 評価できる点

- **C-2 の発見**: 現行 `/flow` 公開 API に named import source の経路がなく `parseScript` が `KSQL1202` で IMPORT を拒否する、という事実を実コードで確認し、**「engine 無改修」を撤回**した。v2 の段階1 が成立する前提そのものが違っていたので、これは M0 の最大の成果
- **C-1 の確認と分岐の決め方**: 「直接フィールド参照は綴りを保持、明示 alias はバッククォート付きでも小文字化」という具体的な挙動を確認し、初期採用を `getFields` 方式、(a) は要件化された場合の切替、と条件を明示した点
- **`--expected-import-sha256`**: FlowNet の path 検査から subprocess 読取までの差替えを閉じる設計。v2 には無かった穴で、TOCTOU を SQL 開始前に潰している
- **preflight の位置**: Attempt 作成後・`setAttemptExecutionStarted` 前。**不在も物理試行として監査・連続回数に数えつつ SQL 未開始を証明できる**という切り分けは正確
- **X-2 の厳格化**: 「単一の重複禁止キーによる `ON DUPLICATE` でなければ `idempotent: true` と宣言できない」。P2-11 三重ゲート③との接続が、v2 の「UPSERT だから冪等」より格段に正確
- **状態モデルの補正(§3.2.5)**: v2 の `REJECTED / INPUT_FILE_MUTATED` は現行モデルに無い形だった。Attempt の `FAILED` と Invocation 前の `REJECTED` を分けたのは正しい

## 2. 要判断(Blocking)

### A-1. 段階1 はもはや「小」ではない — v2 の推奨根拠が崩れている

v2 が「段階1 を先に」と推奨した根拠は **「engine 実装済みなので flow は引数を素通しするだけ、規模は小」**でした。本計画はその前提を否定し(C-2)、見積りは:

| | v2 の見積り | 本計画 |
| --- | --- | --- |
| 段階1 | **小** | **19〜33人日**(M0 1〜2 + engine 前提 2〜4 + kSQL-Flow 4〜7 + FlowNet schema/security 3〜5 + 監査/X-4 4〜7 + 回復/結合 3〜5 + 実測 2〜3) |
| 段階2 | 中 | 17〜29人日 |

§7 の X-4 行に「見積りを小から本書の4〜7人日相当へ修正」とありますが、**修正が必要なのはその1項目ではなく段階1 全体の位置づけです。**

そして 19〜33人日という数字は、**捨てた選択肢を復活させます**。取込アダプタ(FlowNet の外の cron + kSQL CLI + 取込マーカー)は数人日規模で、段階1 に対して得られる差は次の2点だけです:

- IMPORT の検証結果(`#err` の件数等)が **Run の監査に載る**
- 取込が **DAG の順序に入る**(先頭 ASSERT ではなくノードとして)

**この2点に 20〜30人日の価値があるか**を、着手前に明示的に判断すべきです。私は v2 でこの比較を「段階1 は小だから」で済ませていました。前提が変わった以上、再判定が要ります。

判断の材料として、次を計画へ加えることを推奨します。

> §0 へ「代替案との比較」表を置く: 取込アダプタ(数人日・監査は取込マーカーのみ・順序は先頭 ASSERT)vs 段階1(19〜33人日・監査は Run に統合・順序は DAG)。**着手はこの比較の結論をもって行う。**

### A-2. baseline receipt の保存先が「状態は kintone」という設計原則から外れている

§2.2 X-4 と §3.2.4 は、baseline receipt を `KSQL_FLOWNET_IO_DIR/.flownet-meta/runs/<run_id>/inputs/<node_id>.json` へ置き、「共有・耐久ストレージ上の運用メタデータ」としています。

これは**新しいインフラ前提**を持ち込みます。vision §2 と ADR §8 が価値として挙げてきたのは「VPS 1台 + cron 2本 + kintone アプリ3本」で完結すること、状態の耐久ストアは kintone だけ(ローカルは `.ksql/lock-<profile>.json` のような補助層)という構成です。receipt を FS に置くと:

- **別ホストから resume したとき receipt が無い。** cron / 手動 SSH / GitHub Actions / ポーラーという複数の起動経路が同じ Run を継続しうる設計なので、単一ホスト前提を置くならそれを**不変条件として明記**する必要があります(P2-11 が単一 profile 前提を明記したのと同じ扱い)
- 「共有ストレージ」を前提にするなら **NFS 等が新しい依存**になり、上記の売りが崩れます

**代替案**: sha256 は業務データではないので、**kintone に置けます**。Node Attempt レコードの既存の安全化済み文字列フィールド(`result_message` 等)に、`{source名, sha256(64hex), bytes}` を安全な形式で載せれば:

- schema 変更なし(X-4 の「専用列を追加しない」という判断はそのまま維持できる)
- **単一ホスト前提も共有 FS も不要**
- 既存の revision fencing と耐久性がそのまま効く
- クラッシュ時も Attempt レコードが残るので比較元を失わない(FS receipt を置く動機そのものが満たされる)

64hex × 入力ソース数なので、文字列長も現実的です。**この代替を検討したうえで FS を選ぶなら、その理由と前提(単一ホスト or 共有 FS)を明記**してください。

### A-3. 受入18 が依存する engine 意味論が M0 で未確認

受入18(「import 書込 chunk 途中クラッシュ → resume で行重複なし」)は**段階1 の完了条件**に置かれています。しかしこれが成立する根拠は §3.1.2 の

> `ON DUPLICATE` の書込 chunk が途中まで成功して process が落ちても、同じ source の再実行が upsert として収束する**既存 engine 意味論を維持する**

という記述だけで、**M0 のコード確認(§2.1)は C-1 / C-2 の2点しか扱っていません**。「維持する」は確認済みの事実なのか、実装方針の宣言なのかが読み取れません。

特に確認が要るのは、`ON DUPLICATE` の upsert が kintone 側でどう実現されているかです。事前に一括 GET して INSERT / UPDATE へ振り分けているなら、途中クラッシュ後の再実行は前回 INSERT 済みの行を UPDATE に振り替えるので収束します。しかし**kintone の重複禁止制約は「エラーを返す」だけ**であり、engine がそれを UPDATE に変換しているかは実装依存です。

→ **M0 のコード確認へ C-3 として追加**してください。「`ON DUPLICATE` の upsert 判定方式と、部分適用後の再実行が収束することの根拠」。ここが仮定のままだと、段階1 の gate が最後に落ちます。P2-11 が F-01 として「correction 契約が実装上成立すると確認できるまで FROZEN にしない」を置いたのと同じ形です。

## 3. 要修正

### B-1. 入力保持期間の既定30日は、月次業務に対して短い

§2.2 X-5 は保持期間を既定30日とし、「Run 作成日時から保持期限を過ぎた Run は resume / `--rerun-from` しない」としています。

しかし対象は月次締めです。**8月分の締めを10月や11月に補正する**のは業務上ありふれています。30日既定だと、

- 9月末に「8月分の取込をやり直したい」→ すでに期限切れで resume 不可
- 補正 business key で新 Run を作る経路は残るが、**その新 Run にも入力ファイルが必要**で、それも30日で消えている

§2.2 は「運用が30日を超える再開を必要とする場合は、先に保持期間を延ばす」と逃げ道を用意していますが、**既定値が業務周期と合っていないと、最初の1回で必ず踏みます**。

→ **既定を月次周期に合わせる(90日程度)**か、少なくとも「月次 network では 90日以上を推奨」を運用文書へ明記してください。あわせて、**入力ファイルの保持と resume 可能期間は別の概念**であること(アダプタ側がより長く保持してよい)を X-5 に書き分けると混乱しません。

### B-2. 取込アダプタが計画のスコープに無いのに、受入9 がそれを前提にしている

受入9「アダプタが元 path へ保持し、失敗後 resume で読める」の主担当は「運用 adapter + kSQL-FlowNet」となっていますが、**取込アダプタは提案の中の概念であって、まだ存在しません**。本計画の作業表(§3、§6)にも作られていません。

段階1 は「ファイルがそこにある」前提で組まれていますが、**それを置くものが計画のどこにも無い**のがスコープの穴です。

→ 次のどちらかを明記してください。(a) 受入9 は手動配置で実施し、アダプタは別計画とする。(b) 最小の取込アダプタ(ファイル配置 + 取込マーカー)を段階1 のスコープに含め、作業と見積りを加える。受入10(「marker なしは先頭 ASSERT で止まる」)も同じ理由でマーカーアプリの存在を前提にしています。

### B-3. 3リポジトリの協調リリース手順が無い

本計画は engine / kSQL-Flow / kSQL-FlowNet の3つにまたがります。ADR §8 がコストとして挙げた「security fix や schema 変更時に協調 release が必要になる場合がある」が、ここで現実化します。

capability negotiation があるので**古い kSQL-Flow に当たっても安全に落ちる**はずですが、リリース順序が逆になった場合(FlowNet を先に上げた、engine を後で上げた)の挙動が定義されていません。

→ **リリース順序(engine → kSQL-Flow → FlowNet)と、各段での version 互換表**を §6 か §8 へ追加してください。特に「`importCsv` capability を返さない kSQL-Flow に対して `inputs` を持つ network を実行したら、Network ロック取得前に検証エラー」という経路(§3.2.2 で設計済み)を、**リリース途中の状態として受入に含める**のが安全です。

### B-4. FlowNet が sha256 計算のためにファイルを読む点を、不変条件へ書き足す

§3.2.3-5 で FlowNet は「handle を open して sha256/bytes を計算」します。§1 の不変条件1は「業務データ本体は FlowNet の bundle、stdout、kintone 監査アプリを通さない」で、**保存先については正しく守られています**。

ただし Contract §10 の「FlowNet は業務データを見ない」という設計の読み方からは一歩踏み込んでいるので、誤解を避けるため不変条件を精密化してください。

> FlowNet は sha256 / bytes の算出のためにファイルを**ストリーミング読みする**。内容をメモリに保持せず、ログ・Execution Result・kintone・bundle のいずれにも出力しない。

「全量をメモリへ読まない」ことも明記しておくと、1万件を超えた場合の安全側の挙動が保証されます。

## 4. 軽微

- **`INVALID_EXECUTION_RESULT` → `UNKNOWN` は二重検証の結果**(`--expected-import-sha256` で kSQL-Flow 側が既に検証している)。二重自体は fail-closed で妥当ですが、**この経路に到達したら実装バグの可能性が高い**ので、運用文書では「通常発生しない。発生したら二次対応者へ」と位置づけを書いておくと一次対応者が迷いません
- **受入11「件数が監査へ載る」と X-4「専用監査列を追加しない」の関係**が読み取りにくい。`#err` の件数は Execution Result 経由で `result_message` の安全な要約に載る、という理解でよいか明記を
- **§4.3 の出力 pattern が `{node_id}` を許可**し、入力は2種のみという非対称は X-1 の意図どおりですが、**理由(出力は Run 作成後に orchestrator が生成するため)を §4.3 にも1行**書いておくと、後から読む人が「なぜ入力で使えないのか」を §2.2 まで遡らずに済みます
- **§3.1.1-1「standalone kSQL-Flow では `--import-json` も同じ loader 層へ配線してよい」** — 「してよい」は仕様として曖昧。**やる / やらない**を決めてください(contract test の対象範囲が変わります)

## 5. 着手前に片付ける順序(提案)

1. **A-3 を M0 の C-3 として確認**(`ON DUPLICATE` の部分適用後の収束)。受入18 が gate である以上、ここが仮定のままでは着手できない

3. **A-1 の再判定**(取込アダプタ vs 段階1 の比較表を §0 へ。着手はこの結論をもって)
4. B-1〜B-4 を反映
5. そのうえで §6 の順序どおりに着手

**1〜3 はいずれも短時間で決着します。** 特に A-1 は、この計画が明らかにした見積りがあってはじめて判断できるようになったもので、**計画の成果として正しく扱うべき論点**です。「予定どおり進める」ではなく「前提が変わったので選び直す」が、原則4「測定してから作る」に沿った受け止め方だと思います。
